# Gridworks — Static Balance Lab 명세

> 상태: 미개방 개발 도구
>
> Scope 0과 첫 전략공간이 사람 플레이에서 검증된 뒤에만 만들 수 있다.

현재 Scope 0은 사용자가 승인한 cold-LLM proxy로 비전문가 테스트를 임시 대체하지만
`HumanValidationStatus = NOT_COLLECTED`다. 그 결과는 이 문서가 요구하는 사람 플레이 증거를
충족하지 않으며 Lab 개방 조건을 낮추지 않는다.

Static Balance Lab은 게임을 대신 플레이하는 AI가 아니다. 살아남은 규칙의 선택공간이 손으로
검산하기 어려워졌을 때 불가능한 설계, 명백한 지배전략과 민감한 경계를 빠르게 찾는 비권위
정적 도구다. 최종 판정은 권위 시간축과 실제 사람 플레이가 맡는다.

## 1. 왜 지금 만들지 않는가

Scope 0의 핵심 질문은 숫자가 아니라 사람이 세 인과를 읽는가다.

- 서비스 권역과 실제 연결
- 전기 단일고장과 공간 공통원인
- 전력회사 공급과 병원 내부전원

이 질문은 대량 조합, Pareto 전면 또는 LLM agent로 답할 수 없다. 선택률을 목표값으로 맞춘
수치도 재미나 공정성을 증명하지 않는다. 따라서 개발 순서는 다음과 같다.

1. Scope 0 fixture를 작은 표와 손계산으로 검산한다.
2. 코딩 전 카드 테스트로 정보 구조를 검증한다.
3. 별도 승인 뒤 2D playable의 임시 cold-LLM proxy를 실행하고, Lab 개방 전에는 사람 플레이로 다시 검증한다.
4. 살아남은 규칙만 최소 회귀검사로 고정한다.
5. 유효 전략이 세 개 이상이고 손검산이 개발을 막을 때만 Lab을 연다.
6. Lab이 고른 후보도 권위 simulation과 사람 테스트를 다시 통과해야 한다.

## 2. Scope 0에서 허용하는 도구

Scope 0에는 별도 Lab이 없다. `NoBuild`, `RIVER_PARALLEL`, `NORTH_DETOUR`와 `HOSPITAL_E1`,
`OLD_CORRIDOR`의 작은 sanity matrix 또는 짧은 일회성 스크립트만 허용한다.

각 조합에서 다음을 분리해 본다.

- 병원 전력회사 공급
- 병원 P0 연속성
- 마을 공급
- 병원 2회로 의무 통과
- 시작예산과 공기
- 공급·미공급 MWh, 판매, 가스비와 보상

이 표는 다음 오류만 찾는다.

- 발전원까지 닫힌 경로나 병목용량이 없음
- 필수 공사가 공급기한 또는 사건 전에 완공될 수 없음
- 의무가 물리적 최단 완공보다 먼저 활성화됨
- 같은 결과를 내는 비싼 후보 또는 모든 면에서 지배하는 후보
- 싼 후보가 `NoBuild`와 병원 2회로 의무 및 `HOSPITAL_E1` 전력회사 공급에서 같은 결과를 냄
- MWh/GWh와 CashUnit 단위가 닫히지 않음
- 같은 판매·비용·보상이 중복 정산됨

후보 자동생성, optimizer, parameter registry, 보고서 pipeline과 플레이어 모사 AI를 붙이지 않는다.

## 3. Lab 개방 조건

다음을 모두 만족하고 사용자가 별도 승인해야 첫 Lab을 만들 수 있다.

1. Scope 0A와 승인된 Scope 0B가 현재 계약한 이해 검증 gate를 통과했다.
2. 실제 플레이에서 구분되는 전략 원형이 최소 3개 남았다.
3. 비교할 물리·경제 규칙이 권위 시간축과 회귀검사로 이미 구현됐다.
4. 손검산 때문에 반복 개발이 막힌 구체적 증거가 있다.
5. Lab이 답할 한 문장 가설과 active knob 최대 3개가 정해졌다.
6. 예상 출력이 어떤 다음 사람 테스트를 선택하는지 정해졌다.

“나중에 필요할 것 같다”는 개방 근거가 아니다.

## 4. 권위와 책임

- Lab은 제품의 권위 데이터와 이미 열린 Core 계산을 읽는다.
- Lab이 catalog, scenario, 저장게임, 점수 또는 현금을 수정하지 않는다.
- Lab에 제품 산식을 복사하지 않는다.
- 시간에 따른 공사·기동·열·SOC·정산은 권위 시간축이 최종 판정한다.
- 정적으로 안전하다고 한 후보가 권위 실행에서 실패하면 `false-safe` 회귀 결함이다.
- 재미, 이해, 망설임, 위험선호, 실수 회복과 공정성을 자동 판정하지 않는다.
- 별도 서비스나 agent orchestration 없이 기존 CLI의 작은 명령으로 시작한다.

## 5. 파라미터 계약

모든 입력은 다음 여섯 종류 중 하나다.

| 종류 | sweep | 의미 |
|---|---|---|
| `Structural` | 금지 | 틱 순서, P0 자동차단 금지, 계량 경계 같은 규칙 |
| `Derived` | 금지 | 거리에서 얻은 철탑 수, MWh 변환, usable energy |
| `FrozenFixture` | 금지 | 이번 실험에서 고정하지만 결론을 바꿀 수 있는 값 |
| `ActiveKnob` | 허용 | 관찰 근거로 이번 실험에서만 여는 family |
| `Presentation` | 금지 | 경보색, 카메라, UI animation |
| `Removed` | 금지 | 이번 실험에 존재하지 않는 기능 |

고정값도 검증 완료를 뜻하지 않는다. 각 family는 다음 증거 상태를 가진다.

- `UnverifiedFixture`: 구현과 손검산을 위한 시작값
- `ObservedSupport`: 사람 관찰 또는 권위 회귀가 가설을 지지함
- `ReviewRequired`: 결과에 민감하거나 모델과 충돌함

한 gated experiment의 규칙은 다음과 같다.

- 동시에 자동 비교하는 `ActiveKnob`는 최대 3개다.
- 결론을 뒤집을 수 있는 `FrozenFixture + ActiveKnob`는 합계 최대 6개 family다.
- 숫자 표를 한 family로 묶으려면 함께 고정·변경되어야 하며 scalar와 행 수를 기록한다.
- 한 셀을 독립적으로 바꾸면 새 family로 센다.
- 여섯 family로 가설을 닫지 못하면 experiment를 나눈다.
- 한 사람 A/B build에서는 parameter family 하나만 바꾼다.
- 목표 선택률을 만드는 knob는 허용하지 않는다.

## 6. 입력 bundle

Lab이 열린 시점의 한 bundle은 다음 중 **이미 승인된 항목만** 포함한다.

- `BalanceVersion`, catalog와 scenario ID
- 의무 수요 timeline, 우선순위와 authored 차단순서
- 시작 현금, 시작 자산과 열린 설비
- 임무 시작·종료, 공급기한, 경고, 사건과 복구 calendar
- 후보 자산의 가격·공기·정격과 유효 authored 경로
- 정상·폭염·고장 상태의 날씨·수요·가용성
- 판매단가, 발전비, 승인된 DR·비상수단·수리·보상
- 사람이 실제로 이해하고 사용한 전략 원형
- parameter inventory와 각 값의 증거 상태

계약 수락·요금 협상과 모든 가능한 polyline은 자동 변수로 만들지 않는다. 실제 UI가 만든 유효
후보 또는 authored 경로만 비교한다.

전략 원형은 다음처럼 사람 행동을 설명할 수 있어야 한다.

- 가장 싼 radial과 최소 현지대비
- 병원 독립 피더
- 값싼 평시망과 임시 우회
- 사전무장 공장 수요반응
- 계획정지 동안 공급을 검증한 예방정비

실제 플레이에서 사용되지 않거나 설명되지 않은 원형은 넣지 않는다.

## 7. 정적 평가 경계

Lab은 열린 시스템에 필요한 snapshot만 계산한다. 최대 후보는 다음과 같다.

| 경계 | 검사 목적 |
|---|---|
| 정상 피크 | 의무부하, 병목, 판매·발전비와 여유 |
| 폭염 피크 | 수요 증가와 설비 감용 |
| 단일고장 직후 | 살아 있는 경로와 즉시 대응 |
| 사고 +15분 | 지연 자원 도착과 bridge 연속성 |
| 사고 +2시간 | 저장 에너지와 지속 가능한 공급 |
| 복구·결산 | 수리, 보상, LostSales, 현금과 복구시간 |

다음 세 결과를 섞지 않는다.

- `GridReserve`: 온라인 grid-forming 전원이 있는 섬에서 실제 도달 가능한 추가 MW
- `HospitalP0Continuity`: 독립 주·예비 경로, UPS와 병원 비상 디젤
- `BlackoutRecovery`: grid-forming 전원과 재기동 절차

병원 내부전원 때문에 네 시간 사건의 `HospitalP0Continuity`가 `NoBuild`와 같은 것은 오류가
아니다. 비교해야 할 추가 가치는 선언된 전기고장 중의 전력회사 계통공급과 계약 이행이다.

병원 내부전원은 Grid Reserve나 전력 판매가 아니다. 배터리는 같은 섬에 온라인 grid-forming
전원이 있을 때만 다음처럼 계산한다.

```text
BatteryEligibleMW(h) = min(MaxDischargeMW, UsableSocMWh / hHours)
```

15분 snapshot에서 10분 뒤 도착하는 피커나 DR은 `0~10분 bridge`와 `10~15분 replacement`가
모두 이어질 때만 적격이다. 정적으로 증명할 수 없으면 안전으로 추정하지 않고
`NeedsTimelineValidation`으로 보낸다.

## 8. 탐색 방식

탐색은 점수가 오를 때까지 LLM이 한 값씩 바꾸는 과정이 아니다.

1. 단위, 보존식과 일정 가능성을 closed-form으로 검사한다.
2. active knob마다 사전 승인한 하·중·상 값만 둔다.
3. knob가 세 개면 최대 `3³ = 27` 조합만 계산한다.
4. 사람이 작성한 전략 원형과 유효 경로만 조합한다.
5. 승인된 안전·복원력 profile을 먼저 적용한다.
6. 같은 profile 안에서만 기말 현금을 비교한다.
7. 경계와 서로 다른 원형을 대표하는 소수만 권위 시간축으로 보낸다.

서로 다른 안전 profile을 하나의 현금 점수로 섞지 않는다. 장기자산 잔존가치를 계산하지 않는
짧은 임무에서 임시수단이 모든 영구자산을 이기면 `TemporaryMeansDominance`를 보고하고 임무
기간·자산 범위·목표를 재검토한다.

## 9. 출력과 경고

각 후보는 사람이 읽을 수 있는 한 표로 다음을 낸다.

- 안전 통과와 최초 실패 규칙
- P0/P1 미공급 에너지, 전체 ENS와 최대 연속정전
- 정상·사건 병목과 최대 부하율
- Grid Reserve, Hospital P0 Continuity, Blackout Recovery
- 저장 최저 usable SOC와 지연 자원 도착시각
- 시작·최저·기말 현금, 판매, 총지출, LostSales와 보상
- 완공일, 공급기한과 사건 전 가용 여부
- 사건별 복구시간
- 기준값 대비 민감도와 결과가 뒤집히는 threshold

자동 경고는 다음에 한정한다.

- 안전한 설계가 0개 또는 1개뿐임
- 한 전략이 모든 stress에서 더 싸고 더 안전하며 더 빠름
- 필수 공사가 기한 또는 사건 전에 완공 불가능함
- 장기 프로젝트가 공사 자원을 막아 모든 대응이 불가능함
- 1% 국소 변화로 결과가 뒤집히지만 UI가 경계를 설명하지 못함
- 정적 안전 후보가 권위 실행에서 실패함
- 임시수단이 모든 영구자산을 지배함
- 자동 원형은 성공하지만 사람이 같은 정보를 보고 반복 실패함

## 10. 결정론과 오류 처리

- 같은 build/runtime/architecture에서는 같은 입력 보고서가 byte-identical이어야 한다.
- 지원 플랫폼 사이에서는 양자화된 판정·원장·사건 결과가 같아야 한다.
- raw floating-point 바이트와 파일 hash의 플랫폼 동일성은 별도 spike 전에는 약속하지 않는다.
- ID 정렬은 tie-break일 뿐 물리 의미가 아니다. ID를 일대일로 바꿔도 결과가 같아야 한다.
- solver 비수렴, NaN과 수치 오류는 플레이어 정전·보상으로 처리하지 않고 중단해 진단한다.

실행시간 예산은 Lab을 실제로 열 때 bundle 크기와 기준 PC를 측정해 정한다. 구현 전 임의의
초 단위 성능을 제품 약속으로 두지 않는다.

## 11. 사람 중심 calibration loop

한 튜닝 라운드는 다음 순서를 지킨다.

1. 관찰 근거가 있는 한 문장 가설을 쓴다.
2. 관련 parameter family 하나와 허용 범위를 연다.
3. bounded sweep 한 번으로 불가능·지배 후보를 제거한다.
4. 소수 후보를 권위 시간축으로 검증한다.
5. 사람에게 후보 순서를 바꿔 플레이시키고 설명·행동·반응시간을 기록한다.
6. 문제와 직접 관련된 국소 sweep을 최대 1~2회만 추가한다.
7. 결정값, 기각 대안, 사람 관찰과 남은 위험을 기록한다.

동의받은 실제 replay는 저장·replay gate가 열린 뒤에만 회귀입력으로 쓴다. 실패 명령을 자동
교정하지 않는다. LLM은 가설, 단위 경계, 테스트와 보고서 요약을 제안할 수 있지만 catalog
수정, 무제한 반복, 최종 숫자 선택과 출시 승인을 맡지 않는다.

## 12. 첫 Lab 완료조건

1. 같은 환경과 bundle에서 동일한 요약을 만든다.
2. 단위 오류, 범위 밖 knob와 Structural/Derived 직접 sweep을 거부한다.
3. 열린 시스템과 승인된 전략 원형만 실행한다.
4. 안전 profile을 현금보다 먼저 적용하고 최초 실패 이유를 설명한다.
5. 일정 불가능, 지배전략, 임시수단 지배와 민감한 threshold를 경고한다.
6. 권위 시간축으로 넘길 shortlist manifest를 만든다.
7. 관련 시스템이 열렸을 때만 권위 결과와의 비교를 요구한다.
8. 도구만으로 재미 또는 출시 통과를 선언하지 않는다.

원전·데이터센터·냉각수 실험은 1.0 bundle과 섞지 않는다. 해당 방향이 열리면
[1.0 이후 방향](../future/POST_1_0.md)의 단계별 parameter inventory로 별도 bundle을 만든다.
