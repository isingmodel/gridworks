# 2D 내부 후보 — 공식 cold LLM 관찰 2회 요약

> 상태: `COMPLETED`
>
> 증거: 동일 build·동일 prompt의 fresh cold LLM 관찰 2회
>
> 해석 상한: `AggregateDecision = NOT_APPLICABLE`, `HumanValidationStatus = NOT_COLLECTED`

## 1. 무엇을 확인했는가

[관찰 01](OFFICIAL_LLM_OBSERVATION_01.md)과 [관찰 02](OFFICIAL_LLM_OBSERVATION_02.md)는 게임·수치·
prompt를 사이에 바꾸지 않고 `gpt-5.6-sol`, reasoning `ultra`, fresh context로 각각 한 번 수행했다.
두 참가자 모두 follow-up·도움·재시작 없이 native 캠페인을 `SUCCESS`로 끝내고 다음 핵심을
독립적으로 설명했다.

- 미완공 자산의 무전압과 선로 span 제한
- 변전소 권역과 실제 source 경로의 차이
- 병원 이중회선의 전기·공간 독립
- 가스발전소의 부지가격·접속거리 교환과 접속 전 출력 0
- 예방정비가 폭염 derating 중 노후 feeder를 지키는 효과와 실제 공급 기준 결산

첫 참가자는 여기에 support 수가 비용·공기를 늘리고 폭염이 마을 수요를 `1.0 → 1.5 MW`로
바꾼다는 세부사항까지 설명했다. 두 번째 참가자는 기존 발전원 우선 급전과
`distanceSquared ≤ 16`을 더 명시적으로 설명했다.

관찰 01은 가까운 고가 부지, 관찰 02는 먼 저가 부지를 골랐고 둘 다 전량공급에 도달했다. 이는
서로 다른 두 선택이 이 fixture에서 실행 가능했다는 진단일 뿐, 밸런스나 선택 분포를 증명하지
않는다.

| 항목 | 관찰 01 | 관찰 02 |
|---|---:|---:|
| app `FINAL.elapsedMs` | `736,618 ms` | `1,008,269 ms` |
| 발전소 부지 | 가까운 고가 부지 | 먼 저가 부지 |
| final cash | `3.700 M` | `3.900 M` |
| rejected command | `SPAN_TOO_LONG` 2회, 스스로 수정 | 0회 |
| terminal | `SUCCESS` | `SUCCESS` |

이 표는 성공률이나 평균시간을 계산하기 위한 표본이 아니다.

## 2. 개선할 점

다음 순서는 작은 수정으로 다음 사람 관찰의 혼선을 줄일 가능성과 증거 반복성을 함께 고려한 것이다.

### 우선 1 — 내부 코드 대신 플레이어 문구 사용

두 참가자 모두 발전소 부지의 영어 식별자형 이름을 언급했다. 두 번째 참가자는 `SPAN_TOO_LONG`과
`P0`도 덜 다듬어진 표현으로 지적했다.

가장 작은 개선은 machine ID를 규칙·진단에만 남기고 화면에는 다음처럼 한국어 표시명을 쓰는 것이다.

- `NEAR_EXPENSIVE_SITE` → `가까운 고가 부지`
- `FAR_CHEAP_SITE` → `먼 저가 부지`
- `SPAN_TOO_LONG` → `선로 구간이 너무 깁니다 · 지지물을 더 가까이 놓으세요`
- `P0` → `병원 필수부하` 또는 `병원 필수부하(P0)`

새 localization framework나 용어 사전을 만들 필요는 없다. 현재 노출 문구만 바꾸면 된다.

### 우선 2 — 발전소 부지 선택의 시각·비용 경계 명확화

첫 참가자는 부지가격은 보이지만 최종 부지+접속 비용을 발주 전에 알기 어렵다고 했고, 두 번째
참가자는 먼 부지 marker와 실제 selectable anchor가 한 칸 어긋나 보인다고 했다.

가장 작은 개선은 다음 세 가지다.

1. marker 중심과 실제 selectable grid anchor를 정확히 맞추고 hover·keyboard focus에서 같은 cell을
   굵게 표시한다.
2. 선택한 anchor 좌표를 preview에 표시한다.
3. 부지 견적 옆에 `발전소·부지 비용이며 접속선 비용은 별도`라고 명시한다.

아직 경로를 그리지 않은 시점의 총 접속비를 예측하는 auto-route나 비교 optimizer는 만들지 않는다.

### 우선 3 — 새 게임 진입과 도움말의 관계 명확화

두 실행 모두 `새 게임` 직후 조작 도움말을 닫은 뒤 지도로 들어갔다. 첫 참가자는 이를 예상 밖으로
보고했고 두 번째도 같은 동작을 수행했지만 혼란으로 보고하지는 않았다. 따라서 반복된 진입
동작과 한 참가자의 혼란 보고를 구분한다.

가장 단순한 선택은 새 게임을 곧바로 지도에 시작하고 타이틀·메뉴의 `조작 도움말`을 그대로 두는
것이다. 첫 실행 안내를 유지하려면 overlay의 목적과 닫기 버튼을 `조작 안내 · 게임 시작`처럼
명확히 쓰는 정도면 충분하다. 별도 tutorial이나 단계별 popup은 추가하지 않는다.

### 우선 4 — terminal 결과를 직접 선언

첫 참가자는 성공 결산과 action 부재로 terminal을 추론했지만 `승리` 또는 `캠페인 완료` 문구가
없다고 보고했다. 두 번째는 terminal stage를 올바르게 인식했으므로 blocker는 아니다.

최종 제목에 `캠페인 완료 · 성공`을 한 줄 추가하고, 현재 결과 수치와 원인 설명은 그대로 두는
문구 수정이면 충분하다.

## 3. 바꾸지 않을 것

- 두 실행만으로 숫자, 부지 비용, 정비 비용과 승패 조건을 조정하지 않는다.
- core rule을 더 설명하려고 긴 tutorial, 새 화면, route estimator나 telemetry를 추가하지 않는다.
- 두 성공을 성공률·평균시간·사람 검증으로 표현하지 않는다.
- 추가 LLM 반복을 자동으로 열지 않는다. 다음 판단은 처음 보는 사람의 작은 관찰이 소유한다.

두 참가자가 핵심 규칙을 이미 설명했으므로 우선순위는 규칙 추가가 아니라 **노출 문구, 부지 anchor,
진입·종료 신호의 명료화**다.
