# Gridworks — 2D 게임 완성 로드맵

> 문서 상태: 계획

이 문서는 현재의 두 검증용 구현에서 출발해 하나의 완성 가능한 2D 게임에 도달하는 순서를
정한다. 로드맵에 적힌 기능은 backlog나 구현 승인이 아니다. 한 번에 한 단계만 별도 승인해 열고,
그 단계의 결과를 검토한 뒤 다음 단계를 유지·축소·삭제한다.

현재 활성 단계와 다음 제안은 루트 [README](../README.md), 완료 증거는
[로드맵 체크리스트](ROADMAP_2D_CHECKLIST.md)가 소유한다. 제품의 안정된 경험 원칙은
[게임 기획서](product/GAME_DESIGN_KO.md)가 맡는다.

## 1. 출발점

현재 저장소에는 서로 다른 질문을 검증한 두 개의 완성된 수직 slice가 있다.

- [강변 병원 회랑](scopes/SCOPE_0B_PLAYABLE.md)은 고정된 마을·병원, 미리 작성된 공급 경로와
  한 사건을 사용해 서비스 권역, 전기 사고, 공간 공통원인, 내부전원과 정산을 검증했다.
- [수동 선로 건설](scopes/SCOPE_1_INTERACTION.md)은 고정된 source·target 사이에 지지물을 직접
  놓고 거리 제한을 지키며 발주·완공하는 상호작용을 검증했다.

둘은 의도적으로 별도 Core 세션, fixture와 Godot 장면이다. `CorridorDesign`, 정확히 두 개의
수요처, 고정 endpoint 같은 가정을 일반 제품 모델로 확장하지 않는다. 과거 구현과 자동검사는
회귀 기준으로 보존하고, 첫 통합 단계에서 하나의 작은 제품용 장면·세션·시나리오 권위를 새로
시작한다.

## 2. 완성으로 부를 최소 2D 제품

1.0은 한 지도에서 이어지는 세 장의 짧은 캠페인이다.

1. **첫 점등**: 변전소와 선로를 직접 지어 마을에 처음 전기를 공급한다.
2. **두 번째 심장**: 병원에 주 경로와 실제로 독립적인 예비 경로를 만들고 비용을 감당한다.
3. **열돔 아래**: 공장 증설, 예방정비와 예고된 폭염·노후 회선 사용불가에 대비한다.

플레이어는 한 종류의 가스발전소, 배전 변전소, 지지물과 선로를 직접 배치한다. 공사는 비용과
시간을 사용하고 완공 전에는 전기를 전달하지 않는다. 완공 자산은 whole-project 단위의 유상
철거로 재구성할 수 있다. 마을·병원·공장은 authored 수요처이며, 단순 연결과 경로 병목으로
공급을 판정한다.

병원에는 이중 경로와 제한된 UPS·디젤이 있다. 마지막 장에는 고정된 폭염, 이름 붙은 노후 회선의
사용불가, 예방정비 한 종류와 유상 공장 수요감축 한 종류가 있다. 판매, 발전비, 미공급 보상과
현금 결산을 제공하며, 예고 타임라인과 `왜?` 설명이 선택과 결과를 연결한다.

제품 골격에는 새 게임·이어하기, 안전 경계 저장, 장 재시작, 화면·UI 크기·음량 설정이 포함된다.
최종 단계에서 원본 2D 아트, 최소 VFX·SFX, 라이선스 고지와 설치 가능한 빌드를 만든다.

### 1.0에서 제외하는 것

- 3D, 아이소메트릭 카메라를 위한 별도 시스템, 절차 생성과 sandbox
- 여러 발전 기술의 포트폴리오, 배터리와 수동 발전기 출력
- DC/AC 전력조류, 연속 열·주파수·전압 simulation과 외부 solver 런타임 의존
- 확률 고장, 숨은 주사위와 상세 수리 logistics
- 선로 일부 편집·철거, 여러 공사팀과 drag scheduler
- cloud 저장, 계정, 업적, replay 제품, multiplayer와 live service
- 프로젝트 금융, 원전·데이터센터·공유 냉각수
- 대화 tree, cinematic, voice-over와 범용 localization framework

제외 항목은 자동으로 다음 버전의 backlog가 되지 않는다. 현재 모델로 관찰된 선택을 설명할 수
없을 때만 별도 승인으로 다시 검토한다.

## 3. 구조 원칙

### 하나의 제품 경로

첫 통합 단계부터 다음 네 소유자를 하나씩만 둔다.

- 제품 시나리오 데이터 한 개
- 엔진을 참조하지 않는 제품 Core 세션 한 개
- 기본 실행 Godot 장면 한 개
- 현재 제품 전체 흐름을 검사하는 자동검사 한 개

기존 Scope 0B와 Scope 1 타입은 회귀용으로 남기며 제품 타입의 기반 클래스나 공용 command bus로
만들지 않는다. 새 단계마다 현재 제품 경로를 확장하고 두 번째 제품 scene이나 병렬 규칙 엔진을
만들지 않는다.

### 지금 필요한 구조만 만든다

DI container, ECS, plugin 시스템, 범용 편집기, 미래 저장 field와 사용하지 않는 interface는 만들지
않는다. 동일한 코드가 실제로 세 번 반복되기 전에는 추상화를 목표로 삼지 않는다. runtime JSON에는
검사용 정답이나 witness를 넣지 않고, 검증용 경로는 검사 코드가 소유한다.

### 규칙과 화면의 경계

Core는 배치 가능 여부, 연결, 용량, 시간, 현금과 원인을 계산한다. Game은 pointer를 정수 grid
위치로 한 번 변환하고 Core preview·command를 호출한 뒤 반환 상태를 그린다. Game이 거리, 전력,
비용이나 사건 결과를 다시 계산하지 않는다.

## 4. 단계 요약

```text
첫 점등 통합
→ 발전소 직접 건설
→ 유상 철거·재구성
→ 병원 신뢰도·경제
→ 예고된 폭염·정비·대응
→ 저장·설정
→ 3장 캠페인 콘텐츠
→ 2D 표현·패키징
```

의존성은 이 한 줄뿐이다. 중간 단계를 병렬로 구현하거나 뒤 단계의 schema를 미리 만들지 않는다.

## 5. 단계 1 — 첫 점등 통합본

### 플레이어 결과

하나의 native 지도에서 기존 발전원으로부터 시작한다. 배전 변전소를 허용 부지에 놓고, 지지물을
직접 배치해 선로를 연결한 뒤 전체 공사를 발주한다. 시간이 지나 완공되면 서비스 권역 안의
마을이 켜지고 첫 매출과 짧은 결과 보고가 나타난다.

### 포함

- 기존 온라인 발전원과 고정 접속 terminal
- 플레이어가 배치하는 배전 변전소 한 종류
- Scope 1에서 검증한 방식의 지지물·선로 한 종류
- 한 개의 마을과 고정된 서비스 권역 규칙
- 정수 grid, 부지·충돌·인접 구간 최대 길이
- 한 개의 공사 자원, 비용, 공기와 원자 시운전
- 단순 연결과 한 개의 경로 병목
- 실제 인도 전력만 매출로 계산하는 짧은 결산
- 지도, 선택 상세, 공사 상태와 결과를 한 장면에서 보여주는 UI

### 제외

발전소 신규 건설, 병원, 사건, 철거, 공장, 지형별 비용, 분기·mesh, 저장과 캠페인은 열지 않는다.

### 검증

- 부지·충돌·거리·endpoint와 실패 시 상태 불변
- 서비스 권역과 실제 통전의 분리
- 공사 중 무전압과 완공 경계의 원자 편입
- 비용·시간·판매의 보존과 결정론
- 실제 map input 경로와 standard button을 통과하는 headless wiring smoke
- 기존 Scope 0B와 Scope 1 회귀
- 처음 보는 사람이 `놓기 → 연결 → 완공 → 점등`과 `권역 ≠ 공급`을 이해하는지 작은 관찰 한 번

### 완료조건

새 게임에서 결과까지 기본 실행 장면 하나로 끝낼 수 있고, 자동검사가 모두 통과하며, 다음 단계가
의존할 배치·연결·완공 행동을 실제로 한 번 확인한다. 관찰된 모든 major 문제는 수정하거나 기능을
자르거나 소유자가 명시적으로 수용한다.

## 6. 단계 2 — 발전소 직접 건설

### 플레이어 결과

플레이어가 한 종류의 가스발전소 위치를 직접 고르고 발주·완공·접속한다. 발전소가 온라인이 되면
자동급전이 늘어난 수요를 공급한다. 위치는 선로 길이, 공기 또는 비용 중 적어도 하나를 실제로
바꾼다.

### 포함

- 발전소 footprint, 허용 건설영역과 접속 terminal
- 정격, 건설비·공기, 변동비와 온라인 상태
- 선로를 통한 접속과 단순 자동급전
- 위치 비교 preview와 결과 설명

### 제외

여러 발전 기술, 수동 출력, 기동 제약, 연료 조달, 주민정치와 상세 발전소 운영은 열지 않는다.

### 검증과 완료조건

부지 밖·겹침을 거부하고, 미완공·미접속 발전소는 출력하지 않으며, 용량 경계와 원자 편입을
자동검사한다. 전달된 전력만 매출이 되는지도 확인한다. 직접 배치한 위치가 임무 결과를 바꾸지
않으면 기능을 더하지 않고 부지·거리 규칙을 먼저 다시 본다.

## 7. 단계 3 — 유상 철거와 재구성

### 플레이어 결과

완공된 자산이나 지지물을 선택하면 실제로 제거될 전체 package, 비용, 시간과 예상 미공급이 먼저
보인다. 확인하면 package가 즉시 격리되고, 공사가 끝난 뒤 원자적으로 제거된다. 플레이어는 장을
처음부터 다시 시작하지 않고 망을 다시 지을 수 있다.

### 포함

- whole `LineProject`와 연결 자산을 자동 확장한 철거 package
- 확인 전 대상·연결·비용·완료시각·서비스 영향 preview
- 공사 시작의 원자 격리와 완료의 원자 제거
- 건설과 공유하는 한 개의 공사 자원
- 철거 이후 일반 규칙으로 계산되는 미공급과 현금

### 제외

부분 선로 편집, salvage·환급, 미완공 발주 취소, 재사용 자재와 여러 공사팀은 열지 않는다.

### 검증과 완료조건

package closure, orphan node·span 부재, 실패 불변, 격리 이후 공급·현금과 결정론을 자동검사한다.
모든 허용 철거가 graph를 깨뜨리지 않고, 확인 전에 영향이 보이며, 유효한 재구성이 가능해야 한다.

## 8. 단계 4 — 두 번째 심장: 신뢰도와 경제

### 플레이어 결과

병원에 주 경로와 예비 경로를 직접 만든다. 플레이어는 전기적 단일고장과 같은 공간 회랑을 잃는
사건이 다르다는 것을 지도에서 판단한다. 사고 뒤에는 병원 내부전원, 전력회사 공급, 서비스와
현금을 각각 확인한다.

### 포함

- 명시적 terminal graph의 결정론적 reachability
- 선로 project별 전기 회로 경계와 authored 공간 위험 polygon
- 마을과 병원, 병원 UPS·디젤
- 경로의 가장 작은 정격을 이용한 병목
- 판매, 발전 변동비, 미공급 보상과 현금에 반영하지 않는 LostSales 진단
- 선택·사건·결산의 `왜?` 설명

필수 안전·공급 의무는 hard condition으로 둔다. 기말 현금은 안전 조건을 통과한 설계의 결과로
나란히 보여주며, 가중 총점이나 별점으로 병원 안전과 돈을 교환하지 않는다.

### 제외

부분부하 차단, 수동 switch, 확률 고장, 상세 보호계전과 전력조류 solver는 열지 않는다.

### 검증과 완료조건

경로·용량, 전기 단일고장과 공간 제거의 분리, 내부전원 비판매, 에너지·현금 보존, 첫 실패 원인을
자동검사한다. 작은 authored 전략 표로 불가능한 설계와 명백한 지배전략도 검산한다. 값싼 공유회랑과
비싼 독립회랑의 서비스 결과가 실제로 달라야 하며, 화면의 원인 설명은 Core 결과와 일치해야 한다.

## 9. 단계 5 — 열돔 아래: 일정과 위기

### 플레이어 결과

플레이어가 예고 타임라인을 보고 공사와 정비 순서를 정한다. 폭염과 이름 붙은 노후 회선의
사용불가가 오기 전에 준비하고, 위기 중에는 유상 공장 수요감축을 한 번 선택한다. 복구 뒤 이전
결정이 서비스와 돈을 어떻게 바꿨는지 결산한다.

### 포함

- 정수 시각, 일시정지·빠른 진행과 중요 경계 자동정지
- 한 개의 공사 자원과 겹칠 수 없는 공사·정비
- authored 수요 증가와 노후 회선의 고정 유효정격 감소로 표현한 폭염
- 노후 회선의 `정상 → 사용불가 → 복구` 사건
- 예방정비 한 종류
- 공장과 고정 기간의 유상 수요감축 한 종류
- readable forecast timeline과 사건 결과 보고

폭염의 수요 증가와 정격 감소는 각각 손검산·회귀한 뒤 통합한다. 연속 온도나 도체 열상태를
simulation하지 않는다.

### 제외

확률 고장, 상세 열모델, 배터리, 블랙스타트, 수리 logistics와 drag scheduler는 열지 않는다.

### 검증과 완료조건

같은 분에 일어나는 사건 순서, deadline 가능성, 공사 자원 배타성, 정비 효과, 수요감축 기간·비용,
복구와 정산, 모든 실패의 상태 불변을 자동검사한다. 작은 전체 흐름 관찰에서는 사고가 숨은 주사위가
아니라 이전 선택의 결과로 읽히는지 기록한다. 위기가 자동 애니메이션에 불과하면 기능을 추가하지
않고 현재 선택 구조를 다시 설계한다.

## 10. 단계 6 — 저장 가능한 제품 골격

### 플레이어 결과

`Title → New Game/Continue → Pause → Save & Quit → Continue/Restart Chapter` 흐름과 최소 설정을
사용할 수 있다.

### 포함

- 캠페인 슬롯 한 개
- 안전한 simulation 경계의 autosave와 `Save & Quit`
- 장 시작 checkpoint와 `Restart Chapter`
- version을 가진 JSON, 임시파일 후 atomic replace
- 창/전체화면, UI scale, master·ambient·SFX와 조작 도움말 설정
- 한국어 단일 언어

### 제외

cloud, replay, 계정, 여러 profile, achievement와 범용 migration framework는 열지 않는다.

### 검증과 완료조건

모든 공사·사건 경계의 저장 round-trip, 저장 직전·재개 직후 결과 동일성, 잘린 파일·손상 파일·알 수
없는 version의 안전한 거부, 설정 지속을 자동검사한다. 강제종료 뒤 마지막 안전 경계로 돌아오고,
손상된 저장이 새 게임 시작까지 막지 않아야 한다.

## 11. 단계 7 — 세 장 캠페인 콘텐츠

### 플레이어 결과

같은 지도와 이어지는 망 상태로 `첫 점등 → 두 번째 심장 → 열돔 아래`를 처음부터 끝까지 플레이한다.
짧은 업무 브리핑, 예보, 마감과 결과 보고가 이야기의 전부다. 플레이어의 자산과 선택이 다음 장의
출발 조건이 된다.

### 포함

- 각 장의 시작 상태, 의무, 기한, 사건과 reference completion
- 이전 장 자산·현금의 명시적 carry-over
- 상황에 맞는 짧은 tutorial과 언제든 다시 보는 도움말
- 의도된 실패, 장 재시작과 softlock 방지

### 제외

인물 대화 tree, cutscene과 voice-over는 열지 않는다. 같은 시스템을 새롭게 조합할 가치가 확인되지
않으면 고정 challenge도 출시조건에 넣지 않는다.

### 검증과 완료조건

각 장의 최소 한 개 reference completion, 의도된 실패·재시작, carry state, 기한과 최소 공기,
중복정산·softlock 부재를 자동검사한다. 전체 캠페인 관찰에서는 이해, 공정성, pacing과 다시 하고
싶은 이유를 기록하되 통계적 합격률로 포장하지 않는다. 콘텐츠 lock 뒤에는 새 mechanic을 추가하지
않고 모든 briefing의 약속과 실제 규칙을 일치시킨다.

## 12. 단계 8 — 2D 출시 품질과 패키징

### 플레이어 결과

산업 생존 분위기의 원본 2D 지도·설비·상태 overlay와 최소 VFX·SFX가 적용된다. 지원한다고 명시한
운영체제의 깨끗한 설치에서 세 장 캠페인을 끝내고 저장·재개할 수 있다.

### 포함

- 통전·계획·공사·철거·사용불가를 색과 pattern·label로 함께 표현
- 1280×720과 1920×1080 16:9, UI scale과 한국어 typography
- 표준 control의 keyboard focus와 핵심 상태의 접근성 이름
- 차단기·점등·사용불가와 최소 ambient SFX
- credits, 제3자 자산 목록, 라이선스와 설치 안내
- 지원 플랫폼별 설치 가능한 package

카메라 이동, 3D, cinematic, voice-over와 localization framework는 실제 가독성·출시 요구가 없으면
추가하지 않는다. 현재 문서의 `PC/macOS` 표현은 이 단계 전에 Windows+macOS인지 macOS-only인지
확정하고, 실제 검증하지 않은 플랫폼은 광고하지 않는다.

### 검증과 완료조건

clean checkout build, 전체 회귀, package smoke, 화면 layout, 성능·메모리 예산을 검사한다. 지원하는
각 운영체제에서 fresh install, save/resume, display/audio/input과 전체 캠페인을 수동으로 확인한다.
열려 있는 critical 문제가 없고 모든 major 문제를 수정·기능 삭제·소유자 수용 중 하나로 닫아야
한다. 알려진 minor issue, 최종 build 식별값, changelog, 라이선스와 설치 지침을 남긴 뒤 소유자가
출시를 수용한다. 이전 공개판과의 upgrade 호환은 실제로 그 약속이 생길 때 별도 기준으로 연다.

## 13. 검증 정책

### 강한 합격·실패를 쓸 곳

다음은 결과가 기계적으로 참 또는 거짓이므로 이진 판정을 유지한다.

- schema와 strict loader
- 거리·경로·용량·현금·에너지 보존식
- 명령의 상태전이, 실패 불변과 원자 변경
- build, crash, softlock과 save 손상
- 결정론적 reference oracle

### 관찰로 남길 곳

이해, 발견 가능성, 혼란, 공정성, 재미와 다시 하고 싶은 이유에는 숫자식 통과율을 쓰지 않는다.
각 관찰은 `확인됨 / 문제 관찰 / 미관찰`과 심각도로 기록한다. `critical`은 crash·data loss·softlock
또는 핵심 흐름 완료 불가, `major`는 핵심 판단을 막거나 잘못 이끄는 문제, `minor`는 우회 가능한
불편을 뜻한다. 기능과 관찰 측면의 단계 종료에는 다음 네 조건이 필요하다.

1. 기계 불변식이 통과했다.
2. 미해결 critical 문제가 없다.
3. major 문제를 수정했거나, 기능을 잘랐거나, 소유자가 명시적으로 수용했다.
4. 다음 단계가 의존할 실제 행동을 한 번 확인했다.

이 네 조건과 별도로 문서 최신화와 한 번의 독립 검토를 마쳐야 단계 기록을 닫는다.
네 번째 항목은 개발자·소유자의 native 수동 확인으로도 충족할 수 있다. 아래 세 지점의 별도 사람
관찰과 같은 뜻은 아니다.

### 사람과 LLM 플레이

사람 관찰은 세 지점에 집중한다.

- 첫 통합 상호작용
- 전체 위기 흐름
- release candidate 전체 캠페인

LLM 플레이는 매 단계의 기본 완료조건이 아니다. 자동검사와 소유자 검토 뒤에도 한 문장짜리
상호작용 질문이 남을 때만 최대 한 번의 임시 smoke를 별도 승인한다. 불리한 결과를 교체하거나
재실행하지 않고, 결과를 사람·밸런스·출시 증거로 사용하지 않는다. 플랫폼과 앱이 이미 남기는
최소 원본만 사용하며 transcript·runner·manifest 체계를 새로 만들지 않는다.

## 14. 로드맵 중단 조건

단순 connectivity와 capacity가 관찰된 결과를 설명하지 못하거나, 서로 구별되는 전략이 세 개 이상
생겨 손검산이 실제 개발을 막을 때만 로드맵을 멈추고 물리 또는 정적 밸런스 도구를 별도 검토한다.
그 전에는 상세 전력조류, Thermal Lab, Battery Lab과 자동 튜닝을 열지 않는다.

단계 중간에 더 큰 기능이 필요해 보여도 현재 단계의 완료조건을 바꾸지 않는다. 그 기능을 빼고도
플레이어 결과가 성립하는지 먼저 확인하고, 필요성이 실제 관찰로 남았을 때만 로드맵 자체를 다시
검토한다.
