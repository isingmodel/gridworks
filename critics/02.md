# 전체 판정

이번 업데이트는 **표면적인 수정이 아니라 개발 전략의 실질적인 방향 전환**입니다. 이전 버전의 가장 큰 문제였던 “플레이어블보다 밸런스·결정론·검증 인프라를 먼저 만드는 순서”는 명확히 뒤집혔습니다. `Scope 0 Player Test`를 현재 유일한 승인 범위로 두고, 자유 배선·DC 전력조류·열보호·저장·리플레이·3D·Static Balance Lab을 모두 조건부 후보로 내린 것은 적절합니다. 최신 커밋도 이 방향으로 문서 전체를 광범위하게 수정했습니다.

다만 현재 상태를 그대로 판정하면 다음과 같습니다.

| 대상                        | 판정                           |
| ------------------------- | ---------------------------- |
| **Scope 0의 범위와 개발 순서**    | **GO에 가까움**                  |
| **Scope 0의 현재 A/B 실험 설계** | **NO-GO**                    |
| **Godot 구현 착수**           | 핵심 선택 구조 수정 후 **조건부 GO**     |
| **1.0 전체 구현**             | 여전히 **NO-GO**, Gate 0 증거가 먼저 |
| **장기 원전·데이터센터 설계**        | 비전으로 유지 가능, 현재는 과도하게 상세      |

가장 심각한 문제는 범위가 아닙니다. 이제는 오히려 **Scope 0가 검증하려는 핵심 선택 자체가 형식적으로 무너져 있다는 것**입니다.

# 1. 이전 리뷰에서 실제로 해결된 사항

## 1.1 플레이어블 우선 순서: 해결됨

현재는 10~15분짜리 2D 플레이어블을 먼저 만들고, 사람에게 다음 질문을 검증하도록 바뀌었습니다.

> 더 싼 공통 경로와 더 비싼 독립 경로 사이에서 고민하는가?
> 사고 결과를 자신의 이전 선택과 연결하는가?

이것이 올바른 첫 질문입니다. Static Balance Lab도 현재 비범위가 되었고, 사람 검증 뒤 손계산을 넘어서는 경우에만 개방하도록 변경되었습니다. 이전 버전의 가장 큰 개발 리스크는 제대로 제거되었습니다.

## 1.2 1.0이 자동 실행 목록이 아니라 후보 범위가 됨: 해결됨

`SCOPE_1_0.md`는 이제 명시적으로 “후보 경계”이고, Scope 0가 통과해도 전체 목록이 자동 승인되지 않습니다. 다음 축도 `Interaction`, `Economy`, `Timeline`, `Physics`, `Presentation` 중 하나만 열도록 했습니다. 이는 바이브 코딩과 에이전트 개발에서 특히 중요한 통제 장치입니다.

## 1.3 자유 경로와 고충실도 시뮬레이션의 선구현: 해결됨

현재 권위 모델은 다음뿐입니다.

```text
연결 여부
→ 경로 병목용량
→ P0/P2 우선순위 공급
→ 고정 사고 그룹 제거
```

DC 전력조류, 리액턴스, 손실, 열 적분, 주파수, 자동급전은 실제 플레이 문제를 단순 그래프로 설명할 수 없다는 증거가 생길 때만 개방됩니다. 이전 버전보다 훨씬 합리적입니다.

## 1.4 장기자산의 120일 왜곡 문제: 상당 부분 해결됨

1.0 후보 문서에서는 짧은 평가기간과 잔존가치 0이 임시수단을 구조적으로 유리하게 만들 수 있다고 명시했습니다. 신규 발전소도 일정·경제 검산을 통과하기 전에는 비용·공기조차 확정하지 않도록 바뀌었습니다. 이전의 48M 발전소를 120일 현금으로 비교하던 구조적 모순은 일단 제거되었습니다.

## 1.5 수치·결정론 관련 기술적 문제: 잘 수정됨

기술 명세에서는 이전 지적이 상당히 정교하게 반영되었습니다.

* solver 비수렴은 게임 내 정전으로 정산하지 않고 `NumericalFault`로 중단
* 이전 틱 흐름 재사용 금지
* 열상태는 매 틱 basis point로 반올림하지 않고 더 높은 내부 정밀도 유지
* 자산 ID 재명명에 따라 물리 결과가 바뀌지 않는 property test
* 배터리 70MWh를 usable AC-side 에너지로 명확화
* 피커·DR의 10분 지연을 15분 적격성으로 무조건 인정하지 않고 bridge 검증
* 계통예비력, 병원 내부 연속성, 블랙아웃 복구를 별도 개념으로 분리
* 플랫폼 간 raw floating-point byte identity 요구 완화

이 부분은 이전보다 기술적으로 훨씬 건전합니다.

# 2. 최우선 차단 문제: 현재 A/B 선택은 형식적으로 성립하지 않는다

Scope 0의 현재 숫자는 다음과 같습니다.

| 항목         |        A |         B |
| ---------- | -------: | --------: |
| 건설비        |       8M |       12M |
| 공기         |       2일 |        3일 |
| 고장 시 계통공급  |    전부 상실 | 병원 8MW 유지 |
| 병원 P0 미공급  |        0 |         0 |
| 병원 내부전원 잔여 |       0분 |       미사용 |
| 기말 현금      | 5.71168M |  2.35376M |

즉, B는 A보다 **4M 비싸지만**, 고정 사고에서 추가로 피하는 현금 손실은 다음뿐입니다.

```text
A 사건 현금변화 = -0.71680 M
B 사건 현금변화 = -0.07472 M

B의 사건상 이익 = 0.64208 M
B 추가 건설비    = 4.00000 M
B 순불리         = 3.35792 M
```

두 계획 모두 병원 P0 미공급이 0이므로 같은 안전 결과로 분류됩니다. 제품의 공식 목표가 “안전 게이트를 먼저 통과한 뒤 기말 현금을 최대화”라면, **A가 B보다 공식적으로 우월합니다**. 실제로 문서의 기말 현금도 A가 정확히 3.35792M 더 많습니다.

B의 4M 프리미엄을 같은 유형의 사고에서 회수하려면 약 24.9시간의 누적 사고가 필요합니다.

```text
B가 시간당 피하는 병원 손실
= 8 MW × (20 + 0.18 - 0.115) M/GWh ÷ 1,000
≈ 0.16052 M/시간

4 M ÷ 0.16052 M/시간 ≈ 24.9시간
```

현재 실제 사고는 4시간 한 번뿐입니다.

따라서 현재 테스트는 다음 질문을 검증하지 못합니다.

> 플레이어가 합리적으로 비용과 독립성을 교환하는가?

실제로는 다음을 묻습니다.

> 게임의 공식 경제목표에 반하여, 사용하지 않아도 되는 여유를 감정적으로 구매하는가?

이것은 다른 실험입니다.

# 3. A는 “싼 대안”조차 아니며, 사실상 강제된 미끼다

더 심각한 문제는 A가 현재 모델에서 어떤 실질적 효용도 제공하지 않는다는 점입니다.

* 기존 E1과 같은 `OLD_BAY` 경계를 공유합니다.
* 유일한 고정 사고는 바로 그 경계를 제거합니다.
* 사고 중 A와 E1은 함께 사라집니다.
* 병원 P0는 A가 없어도 내부전원으로 정확히 4시간 유지됩니다.
* “아무 예비 회랑도 짓지 않기”는 선택지에 없습니다.

따라서 모델에 없는 `No Build` 계획을 추가하면 다음과 같습니다.

```text
No Build:
- A와 같은 사건 결과
- A와 같은 P0 결과
- A보다 현금 8M 많음
```

즉, **No Build가 A를 완전히 지배**합니다.

A가 의미 있으려면 최소한 다음 중 하나는 있어야 합니다.

1. A가 독립 회선 고장에는 유효하지만 공통회랑 사고에는 실패한다.
2. A가 먼저 발생하는 계획정지 또는 국소 피더 고장을 한 번 막는다.
3. A가 정상운전 중 다른 수요나 용량 이익을 제공한다.
4. No Build도 정식 선택지로 두고 A의 실제 효용을 관찰한다.

현재처럼 A/B 중 하나를 반드시 짓게 하면, 플레이어가 A를 택했다는 사실은 “의미 있는 트레이드오프”의 증거가 아닙니다. 단지 돈을 아끼거나 구조를 오해했을 가능성이 큽니다.

## 가장 좋은 최소 수정

Scope 0의 두 경로를 다음처럼 바꾸는 것이 적절합니다.

| 계획 | 전기적 단일고장 | 공통회랑 사고 | 비용 |
| -- | -------- | ------- | -: |
| A  | 견딤       | 함께 끊김   | 낮음 |
| B  | 견딤       | 견딤      | 높음 |

즉:

* A는 **별도 전기 회선이지만 같은 공간 회랑**
* B는 **별도 전기 회선이며 별도 공간 회랑**

이렇게 해야 A도 실제 안전가치를 갖고, B가 추가로 사는 것이 “공통원인 위험 대응”으로 명확해집니다.

# 4. 정확히 `4시간 사고 = 4시간 내부전원`은 잘못된 knife-edge다

현재 A는 다음 조건으로 P0를 지킵니다.

```text
UPS 15분
+ 디젤 3시간 45분
= 정확히 4시간

사고 시간
= 정확히 4시간
```

그리고 사고 종료 경계에서 먼저 E1을 복구한 뒤 다음 1분 P0를 판정하여, 한 틱의 정전도 발생하지 않게 규정했습니다. 계산과 이벤트 순서는 일관됩니다. 그러나 게임 설계로는 지나치게 인공적인 경계입니다.

이 구조는 “신뢰도 여유”가 아니라 **이벤트 처리 순서의 정확한 경계값**을 검증합니다.

* 사고가 1분 길면 A는 P0 실패
* 사고가 1분 짧으면 A는 내부전원 1분 잔여
* 현재는 정확히 0분에서 복구
* 플레이어는 고정된 정확한 사고시간도 미리 압니다

“안전 여유를 돈으로 사는 게임”인데, A를 안전 통과시키는 기준은 여유 0입니다. 제품 철학과 정반대입니다.

### 수정 방식

목표에 따라 둘 중 하나를 선택해야 합니다.

#### A와 B를 모두 안전한 선택으로 만들려는 경우

```text
예상 사고: 3~6시간 범위
내부전원: 5시간
실제 fixture 사고: 4시간
```

플레이어에게는 정확한 실제 길이가 아니라 공정한 범위를 제공합니다. A는 알려진 범위 안에서 내부전원에 의존하는 저비용 전략이고, B는 계통공급을 유지해 내부전원을 보존하는 고비용 전략이 됩니다.

#### B가 안전 게이트를 통과하는 유일한 선택이어야 하는 경우

```text
내부전원: 3시간
사고: 4시간
```

이 경우 Scope 0의 목적을 “고민 검증”이 아니라 **공통원인 위험 이해도 검증**으로 좁혀야 합니다. B가 정답인 튜토리얼이기 때문입니다.

현재 문서는 이 두 목적을 섞고 있습니다.

# 5. 정보 공개 계약이 정의되어 있지 않다

A/B 선택의 의미는 플레이어가 선택 당시 무엇을 아는지에 전적으로 달려 있습니다.

현재 문서에서는 정확한 사용불가 시각을 공개한다고 했지만, 다음 정보가 선택 시 공개되는지는 충분히 명확하지 않습니다.

| 정보                    | 공개 여부가 필요한 이유         |
| --------------------- | --------------------- |
| 사고 예상 지속시간            | A 내부전원이 충분한지 판단       |
| 실제 사고가 정확히 4시간이라는 사실  | 공개되면 A가 합리적 최적해에 가까워짐 |
| 내부전원 총 지속시간           | B의 효용 판단              |
| A와 E1이 같은 사고에서 같이 사라짐 | 공통원인 이해               |
| 사고 뒤 추가 사건이 없다는 사실    | B의 남은 여유 가치 판단        |
| 보상단가와 예상 사건비          | 경제적 비교                |
| 기말 현금이 공식 비교 목표라는 사실  | 최적화 기준                |

이것을 `Decision Information Contract` 표로 명시해야 합니다.

예:

```text
플레이어에게 보임:
- 사고 발생 시각
- 예상 지속범위 3~6시간
- 내부전원 현재 지속가능시간 5시간
- A는 OLD_CORRIDOR 사고에 함께 영향
- B는 별도 회랑
- 각 계획의 비용과 완공일

플레이어에게 보이지 않음:
- 실제 사고 지속시간
- 실제 사건 후 추가 고장의 존재 여부
- 사후 oracle 숫자
```

정보 공개를 규정하지 않으면 플레이테스트 결과를 해석할 수 없습니다. A 선택이 합리적 판단인지, 정보 부족인지, UI 오해인지 구분되지 않기 때문입니다.

# 6. 공기 차이는 현재 아무 의미가 없다

현재:

* A 완공: day 3 08:00
* B 완공: day 4 08:00
* 사고: day 9 16:00
* B도 사고 128시간 전에 완료

따라서 A의 “1일 빠름”은 어떤 공급, 수익, 안전 또는 이후 공사에도 영향을 주지 않습니다. 화면에는 비용과 완공일을 비교하게 하지만, 공기 차이는 현재 fixture에서 장식값입니다.

선택 변수가 결과를 바꾸지 않으면 플레이어에게 보여주지 않는 편이 낫습니다.

선택지는 두 가지입니다.

* Scope 0에서는 A/B 공기를 같게 만든다.
* 사고 또는 후속 의무를 당겨 B의 느린 완공에 실제 기회비용을 만든다.

후자는 다른 시간축 가설을 추가하므로, 첫 실험에서는 **공기를 같게 하는 것**이 더 낫습니다.

# 7. 시작 마을의 두 후보 셀은 불필요한 가짜 선택이다

Scope 0는 마을 변전소를 “지정된 두 후보 셀 중 하나”에 놓게 합니다. 그런데 두 후보의 다음 차이가 정의되어 있지 않습니다.

* 가격
* 완공시간
* 서비스 범위
* 수요 포함
* 상위 연결
* 이후 확장성
* 안전성

둘이 동일하면 선택 의미가 없습니다. 다르면 A/B 핵심 가설과 별개의 공간배치 가설이 추가됩니다.

현재 Gate 0의 핵심은 공통경계 대 독립경계입니다. 따라서 첫 마을은 후보 셀 하나로 고정하는 것이 낫습니다.

```text
Scope 0:
고정 셀에 변전소 배치
→ 고정 피더 연결
→ 범위와 실제 연결의 차이 학습
→ A/B 핵심 선택
```

자유 배치 또는 후보지 비교는 `Interaction` 게이트에서 별도로 검증해야 합니다.

# 8. 일부 구현 규칙이 Scope 0에서 실제로 사용되지 않는다

Scope 0에는 다음 규칙이 포함되어 있습니다.

* P0 → P2 공급 우선순위
* 부분 공급률
* 외곽 셀부터 공급 제한 표현
* exact kW-minute 계량
* decision-marker 원자 정산

하지만 현재 fixture에서는 정상수요 32MW, 경로용량 40MW이므로 부분 공급이 없습니다. 사고 때는 경로가 완전히 끊겨 공급률이 0% 또는 병원만 유지됩니다.

따라서 아래 기능은 현재 인간 가설을 검증하지 않습니다.

* 70% 공급 시 외곽 셀 30% 소등
* 같은 경로에서 P0와 P2의 부분 배분
* 셀 단위 부분 공급 표현

이것들은 구현과 테스트를 늘리지만 Scope 0 결과에는 관여하지 않습니다.

첫 빌드에서는 다음 네 상태면 충분합니다.

```text
미연결
연결됐지만 공사 중
통전·공급
사용불가
```

부분공급은 실제로 용량부족 가설을 여는 후속 게이트로 미루는 편이 맞습니다.

# 9. 현재 Scope 0는 “재미”보다 “이해도”를 검증한다

Scope 0의 실제 플레이어 행동은 세 가지입니다.

1. 마을 후보 셀 선택
2. A/B 선택
3. 다음 이정표 진행

사고 중 플레이어가 내리는 운영 결정은 없습니다. 배터리, 감축, 정비, 복구도 없습니다. 따라서 Gate 0가 검증할 수 있는 것은 다음입니다.

* 서비스 범위와 전기 연결을 이해하는가
* 공통원인 위험을 이해하는가
* 선택 결과를 자신의 결정에 귀인하는가
* 비용과 공급연속성 비교가 의미 있어 보이는가

반면 다음은 검증하지 못합니다.

* 위기 대응이 재미있는가
* 운영 루프가 재미있는가
* 건설과 복구의 반복이 재미있는가
* 장기 계획과 단기 대응의 연결이 재미있는가
* 45~90분 세션을 지속할 수 있는가

따라서 문서의 목적을 다음처럼 좁혀야 합니다.

> Scope 0는 핵심 인과관계의 이해도와 선택의 지각된 의미를 검증한다.
> 전체 게임의 재미나 반복 루프는 승인하지 않는다.

Gate 0 통과 후 별도의 `Gate 1: Active Response`가 필요할 가능성이 높습니다. 예를 들어 사고 중 한 번의 배터리 사용 또는 수요감축 선택만 추가하여 `예측 → 선택 → 결과`를 직접 플레이하게 하는 단계입니다.

# 10. 사람 플레이테스트 기준도 수정해야 한다

현재 기준 중 가장 문제가 되는 것은 다음입니다.

> 참가자 집단에서 A와 B가 각각 최소 한 번 실제로 선택된다.

5명 중 한 명이 규칙을 오해해 B를 선택하거나 A를 선택해도 이 기준은 통과합니다. 반대로 모두가 같은 선택을 정확한 이유로 하면 실패합니다.

선택 다양성은 **진단지표**이지 통과조건으로 적합하지 않습니다.

더 좋은 기준은 다음입니다.

* 자신의 선택이 무엇을 포기했는지 설명한다.
* 어떤 조건이 바뀌면 반대 선택으로 전환할지 설명한다.
* 비용이 얼마까지 오르면 B를 포기할지, 사고시간이 얼마면 B를 택할지 말한다.
* A가 실패하는 고장과 B가 실패하는 고장을 구분한다.
* 결과를 본 뒤 선택의 근거가 어떻게 달라졌는지 설명한다.

예를 들면:

```text
5명 중 4명 이상:
- 자기 선택의 장점과 단점을 각각 하나 이상 설명
- 반대 선택이 합리적이 되는 조건을 하나 이상 제시
- 공통고장과 독립고장의 차이를 원인 사슬로 설명
```

A/B 선택 비율은 별도로 기록하되 게이트를 결정하지 않는 편이 낫습니다.

또한 참가자 조건도 “전력망 게임 초보”만으로는 부족합니다. 최소한 다음을 기록해야 합니다.

* 전략·경영 게임 경험
* 전력 또는 공학 배경
* 게임 UI 숙련도
* 유사 인프라 게임 경험

전력망 초보이면서 전략게임 경험이 있는 사용자가 실제 핵심 타깃일 가능성이 높습니다.

# 11. 경로 카드의 문구가 결과를 지나치게 유도한다

현재 Scope 0 경로 카드는 다음을 표시합니다.

```text
A · 8 M · 2 DAYS · SHARED BOUNDARY
B · 12 M · 3 DAYS · INDEPENDENT BOUNDARY
```

`SHARED`와 `INDEPENDENT`는 기술적으로는 정확하지만, 거의 가치판단 라벨입니다. 플레이어가 원인을 이해하지 않고도 “Independent가 안전하겠지”라고 추측할 수 있습니다.

결과 중심 문구가 더 낫습니다.

```text
A
8 M
OLD_BAY 정지 시 E1과 함께 끊김

B
12 M
OLD_BAY 정지 중에도 병원 계통공급 유지
```

테스트 후 인터뷰에서는 라벨을 반복하는 것이 아니라 다음 경로를 직접 설명하게 해야 합니다.

```text
고장 자산
→ 사라지는 회선
→ 남는 공급 경로
→ 병원 내부전원 사용 여부
```

# 13. `scenario.json`을 Codex가 발명하지 않도록 최소 토폴로지 표가 필요하다

Scope 0 문서는 숫자와 결과 oracle은 자세하지만, 실제 그래프 입력은 충분히 구체적이지 않습니다.

최소한 다음 표가 필요합니다.

## 노드

| ID              | 종류         | 위치    | 시작 상태              |
| --------------- | ---------- | ----- | ------------------ |
| `GEN_01`        | Generator  | x,y   | Online             |
| `BUS_PRIMARY`   | Bus        | x,y   | Energized          |
| `TOWN_SUB`      | Substation | 후보 위치 | Unbuilt            |
| `HOSPITAL_SUB`  | Substation | x,y   | Existing           |
| `TOWN_LOAD`     | Demand     | x,y   | Activates D1 08:00 |
| `HOSPITAL_LOAD` | Demand     | x,y   | Active             |

## 간선

| ID          | From    | To       |   정격 | FailureGroup | 시작 상태     |
| ----------- | ------- | -------- | ---: | ------------ | --------- |
| `GEN_FEED`  | GEN     | PRIMARY  | 80MW | `GEN_PATH`   | Existing  |
| `E1`        | PRIMARY | HOSPITAL | 40MW | `OLD_BAY`    | Existing  |
| `A`         | …       | HOSPITAL | 40MW | `OLD_BAY`    | Candidate |
| `B`         | …       | HOSPITAL | 40MW | `NEW_BAY`    | Candidate |
| `TOWN_FEED` | …       | TOWN_SUB | 40MW | `TOWN_PATH`  | Unbuilt   |

## 사고

```json
{
  "startMinute": 12800,
  "durationMinutes": 240,
  "removeFailureGroups": ["OLD_BAY"]
}
```

현재 문서만으로도 인간은 의도를 이해하지만, Codex는 다음을 임의 결정해야 합니다.

* A의 시작 노드와 끝 노드
* E1이 마을까지 공급하는 정확한 topology
* B가 어느 상위 모선에서 출발하는지
* 병원 내부전원의 노드 여부
* 서비스 권역과 수요점 연결
* 좌표와 후보 셀 차이

이것은 구현 중 의미론적 드리프트가 생기기 좋은 부분입니다.

# 14. 정수 화폐의 최소단위를 명시해야 한다

문서는 화폐를 정수 최소단위로 저장하고 fixture 계산이 정확히 닫혀야 한다고 규정합니다. 그러나 다음이 명시되어 있지 않습니다.

```text
1 M = 정수 몇 단위인가?
```

현재 값에는 `0.01248 M`, `0.07472 M`, `5.71168 M`처럼 소수점 다섯 자리까지 필요합니다.

최소한 다음 중 하나를 확정해야 합니다.

```text
1 M = 100,000 MoneyMicro
```

또는:

```text
모든 돈은 1 실제 화폐단위로 저장
1 M = 1,000,000 units
```

후자가 가장 단순합니다. 그러면:

```text
0.01248 M = 12,480 units
5.71168 M = 5,711,680 units
```

이 규칙을 `SCOPE_0_PLAYABLE.md`와 `scenario.json` 예시에 넣어야 합니다.

# 17. 장기 제품의 공식 목표에도 남은 구조적 문제가 있다

업데이트 후 공식 목표는 다음입니다.

```text
1차: 안전·서비스·지급능력 통과
2차: 기말 현금 최대화
```

이는 이전의 혼란스러운 복수 경제지표보다 낫습니다. 그러나 Gridworks의 판타지는 “안전 여유를 돈으로 사는 것”입니다. 안전 게이트를 한 번 통과한 뒤 추가 여유에 가치가 없다면 플레이어는 다음을 하게 됩니다.

> 알려진 모든 사건을 정확히 통과하는 최소설비를 건설한다.

특히 사건이 고정되고 정확히 공개되면 “다음 고장을 버티는 여유”가 아니라 “스크립트에 필요한 최소치”를 암기하게 됩니다.

후속 캠페인에서는 다음 중 하나가 필요합니다.

### 방법 A: 안전 등급을 단계화

```text
Minimum
- P0 유지
- 기본 N-1 통과

Robust
- 내부 비상전원 50% 이상 잔여
- 공통원인 스트레스 통과

Resilient
- 복구 중 전체 서비스율 99% 이상
```

각 등급 안에서 기말 현금을 비교합니다.

### 방법 B: 선언된 스트레스 세트 전체를 통과

한 개의 정확한 사건이 아니라 사전에 공개된 여러 고정 스트레스 케이스를 사용합니다.

```text
- 회선 단독 상실
- 상위 베이 상실
- 4~6시간 공통회랑 사용불가
- 폭염 중 감용
```

실제 캠페인 사건은 하나더라도, 안전 판정은 세트 전체를 기준으로 할 수 있습니다.

### 방법 C: 단일 공식 순위를 포기

다음 결과를 병렬로 보여줍니다.

* 기말 현금
* P0 연속성
* 계통공급 가용성
* 내부 비상전원 최저 잔여시간
* 복구시간
* 공통원인 스트레스 통과

이 방식이 현재 제품 철학에는 더 잘 맞습니다.

# 18. 결정론적 authored 구조는 이제 버그가 아니라 제품 포지셔닝 문제다

업데이트 후에는 고정 이벤트와 authored 회랑이 첫 검증을 위한 의도적 선택임이 명확해졌습니다. 이것은 Scope 0에서는 적절합니다.

하지만 Scope 0 통과가 증명하는 제품은 우선 다음에 가깝습니다.

> 전력망 신뢰도에 관한 authored infrastructure puzzle

아직 다음을 증명하지는 않습니다.

> 반복 가능한 전력망 simulation game

한 지도, 최대 3장, 고정 사건, 고정 회랑을 유지한다면 완성 제품도 퍼즐 캠페인에 가까워질 수 있습니다. 이것은 실패가 아니지만, 개발 중 어느 시점에는 제품 정체성을 명시적으로 선택해야 합니다.

* **퍼즐 중심:** 짧고 정교한 authored 문제, 명확한 학습과 반성
* **시뮬레이션 중심:** 다양한 초기조건, 사건 변형, 장기 운영과 반복성

Scope 0 단계에서는 퍼즐로 시작하는 것이 맞습니다. 다만 그 결과를 근거로 “시뮬레이션 재미가 검증됐다”고 확대 해석해서는 안 됩니다.

# 19. 엔진 선택은 현재 차단 문제가 아니다

`Godot 4.7.1 .NET + C#` 선택은 현재 기준으로 유효합니다. Godot 4.7.1은 2026년 7월 공개된 안정 버전이고, 공식 .NET 빌드 문서는 .NET SDK 8 이상을 요구합니다. 따라서 현재 엔진·SDK 방향을 다시 바꿀 이유는 없습니다. ([Godot Engine][2])

다만 Scope 0에서는 다음만 유지하면 충분합니다.

```text
Gridworks.Core
game/
data/scenario.json
tests/
```

현재 문서가 명시한 것처럼 `Application`, `Persistence`, `Headless`를 미리 만들지 않는 것이 맞습니다.

# 20. 구현 전에 반드시 수정할 우선순위

## P0 — 코딩 전 차단 사항

### 1. `.AGENTS.md`를 `AGENTS.md`로 변경

이것은 즉시 처리해야 합니다.

### 2. A/B 선택 구조를 재설계

현재 공식 목표에서는 A가 우월하고, No Build는 A를 완전히 지배합니다.

최소 수정안:

```text
A: 전기적으로 독립, 같은 공간 회랑
B: 전기적으로 독립, 별도 공간 회랑
```

### 3. `4시간 = 4시간` 경계 제거

* 지속시간 범위를 공개하거나
* 내부전원에 명시적 여유를 두거나
* B만 안전통과하도록 목적을 좁혀야 합니다.

### 4. 선택 시 정보 공개표 추가

사고 시각, 지속시간, 내부전원, 보상, 추가 사건 여부 중 무엇이 보이는지 고정해야 합니다.

### 5. 최소 topology 및 `scenario.json` 예시 추가

Codex가 그래프 의미를 발명하지 않게 해야 합니다.

## P1 — 첫 플레이테스트 전에 수정

### 6. 의미 없는 마을 후보 셀 제거

Scope 0에서는 한 위치로 고정하십시오.

### 7. 공기 차이를 제거하거나 실제 결과와 연결

현재 2일/3일 차이는 아무 효과가 없습니다.

### 8. 부분공급·셀 소등 규칙을 비범위로 이동

현재 fixture에서는 사용되지 않습니다.

### 9. A/B 선택 다양성을 통과조건에서 제거

대신 자신의 선택의 단점과 전환조건을 설명하게 해야 합니다.

### 10. 기술용어 대신 결과 중심 경로 카드 사용

`SHARED/INDEPENDENT BOUNDARY`보다 “어떤 고장 때 함께 끊기는가”를 직접 표시해야 합니다.

## P2 — 구현 진행 중 정리

### 11. 미래 후보 설계를 별도 디렉터리로 격리

`GAME_DESIGN_KO.md`를 활성 제품 원칙 중심으로 축소하십시오.

### 12. `critics/`를 비권위 archive로 이동

Codex 컨텍스트 오염 가능성을 줄여야 합니다.

### 13. 코드·문서·이미지 라이선스 결정

현재 공개 저장소에는 라이선스가 보이지 않습니다. 외부 기여나 자산 재사용 전에 경계를 명시해야 합니다. 저장소 문서도 이를 필요조건으로 이미 언급하고 있습니다.

# 21. 가장 효율적인 다음 검증은 Godot이 아니라 종이 프로토타입이다

현재 핵심 결함은 그래픽이나 코드가 아니라 A/B 의사결정 구조입니다. 따라서 바로 Godot을 만들기 전에 카드 또는 Figma 수준의 `Scope -1` 테스트가 적합합니다.

필요한 것은 다음 네 화면뿐입니다.

1. 간단한 지도와 기존 E1
2. A/B 경로 카드
3. 선택 당시 공개 정보
4. 사고 결과 카드

참가자에게 다음만 묻습니다.

```text
어느 경로를 고르는가?
왜 고르는가?
선택하지 않은 경로가 더 나은 조건은 무엇인가?
사고시간이 몇 시간이면 선택을 바꾸는가?
추가비가 얼마면 선택을 바꾸는가?
```

현재 수치대로라면 상당수는 다음 중 하나를 보일 가능성이 큽니다.

* B가 “독립”이라고 써 있어 B를 선택
* 정확히 4시간을 버티므로 A를 선택
* A가 실제로 아무 역할도 하지 않는다는 사실을 발견
* 추가 현금을 어디에 쓸 수 있는지 몰라 비용 차이를 무시

이 결과를 먼저 확인하면 잘못된 실험을 구현하는 비용을 피할 수 있습니다.

# 결론

업데이트는 성공적입니다. **이제 프로젝트의 실패 위험은 “너무 많이 만들다가 실패”에서 “너무 잘 축소했지만 잘못된 핵심 실험을 구현할 위험”으로 바뀌었습니다.** 이는 훨씬 나은 상태입니다.

하지만 현재 Scope 0는 그대로 구현하면 안 됩니다. 이유는 명확합니다.

> A는 실제 고정 사고에서 아무 효용이 없고, No Build에 지배되며,
> B는 같은 P0 안전등급에서 공식 경제목표상 A보다 약 3.36M 불리합니다.

먼저 `AGENTS.md` 파일명을 바로잡고, A를 실제 가치가 있는 중간 안전설계로 만들고, 선택 시 정보 공개와 사고 지속시간을 재설계해야 합니다. 그 수정 후에는 **Godot 2D Scope 0 구현을 시작해도 되는 수준**입니다.
