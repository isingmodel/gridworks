# Gridworks — Scope 0B 2D playable 후보

> 상태: **미개방 후보**
>
> 개방 조건: [Scope 0A 카드 테스트](SCOPE_0A_CARD_TEST.md)의 현재 계약 판정 통과
> (`LLM-PROXY-R1`에서는 `PROXY-PASS`), 결과에 대한 적응형 점검, 사용자의 별도 구현 승인

이 문서는 다음 단계가 무엇을 검증해야 하는지만 제한한다. 현재 구현 계약이나 backlog가 아니다. Scope 0A에서 관찰된 오해와 성공 근거를 보기 전에는 명령 API, 저장소 구조, fixture 형식, 정확한 화면 배치와 자동검사를 확정하지 않는다.

## 1. 목적

카드에서 이해한 세 인과를 10~15분짜리 직접 조작에서도 설명 없이 사용할 수 있는지 검사한다.

1. 설치된 무전압 마을 변전소의 상위 피더를 연결해 서비스 권역을 통전한다.
2. 예고된 병원 의무와 강변 공간사건을 선형 타임라인에서 읽는다.
3. 강변 병행 또는 북부 우회 중 한 authored 회랑을 짓는다.
4. 두 회랑×두 제거사건의 결과를 선택 전에 예측한다.
5. 고정 사건과 복구 뒤 계통공급, 병원 내부전원과 현금 결과를 원인별로 확인한다.

Scope 0A와 다른 새 게임 가설을 여기에 추가하지 않는다.

## 2. 최대 허용 범위

- 단일 탑다운 2D 지도, 상시 원인 패널, 읽기 전용 예고 타임라인, 종료 overlay
- 기존 가스발전, 마을, 병원, 고정 변전소와 authored 선로만 사용
- 마을 상위 접속공사 하나와 병원 회랑 선택 하나
- 이진 공급, 경로 존재와 공유 병목용량, 고정 절체
- 병원 소유 UPS·디젤과 전력회사 계량을 분리
- 실제 인도 전력 판매, 가스 변동비와 고객별 미공급 보상
- 병원 E1 단일제거와 강변 공간제거의 읽기 전용 결과 비교
- 공사·의무·사건·복구 이정표에서만 시간 진행

자유 배치·경로, 실시간 급전, 부분공급, DC 전력조류, 확률사건, 정비·수리, 저장·replay, 3D,
신규 발전원과 범용 framework는 제외한다. 미래 기능을 위한 빈 interface나 schema field도 없다.

## 3. 승인 시 먼저 다시 쓸 계약

Scope 0B를 승인하는 변경은 다음을 같은 scope 문서에서 새로 닫아야 한다.

- Scope 0A 결과 중 playable에서 다시 검사할 오해 하나
- 카드 fixture에서 새 scope가 정한 단일 machine-readable fixture로의 값·ID·제거행렬·oracle 인계 검사
- 이전 구간 정산, 공사·복구, 사건 시작, 경로 재평가, 내부전원 절체와 새 의무의 경계 순서
- 시작·UPS·디젤·복구 경계에서 P0 공백이 없는 최소 상태전이
- UI가 예측을 막는 책임과 simulation Core의 권위 경계
- 공유 간선 총수요와 발전원 합계가 정격 안인지 확인하는 fixture validator
- 실패 시 상태를 바꾸지 않는 최소 명령과 필요한 smoke test

이 목록은 구현 세부를 선결하라는 뜻이 아니다. 승인 시 Scope 0A 증거에 맞춰 불필요한 항목을
더 제거한 뒤, 한 fixture에 필요한 계약만 작성한다.

## 4. 성공과 종료

성공 기준은 카드 테스트와 겹치지 않는 신규 참가자가 직접 조작에서도 세 인과를 설명하고,
사건 결과를 무작위가 아니라 자신의 회랑 선택에 귀속하는 것이다. 정확한 표본·시간·통과선은
Scope 0A 결과를 본 뒤 고정한다.

조작이 새 오해를 만들면 `Interaction` 문제 하나만 수정한다. 카드에서조차 인과가 통과하지
않았거나, playable을 위해 범용 물리·경제 시스템이 필요해지면 Scope 0B를 열지 않는다.

Scope 0B가 `GO`여도 다음 gate는 결과 점검으로 다시 선정하며, 미개방 후보가 자동으로
활성화되지 않는다.
