# Gridworks 출시판 재구축

> 상태: **ACTIVE**
> 구현 권한: **GRANTED**  
> 현재 작업: **3단계 — 프롤로그·본편 캠페인**
> 승인 근거: 2026-08-17 사용자가 전문적인 한국어 표현, 분기·합류와 설비 용량, 이야기와 실제
> 플레이 장, 더 촘촘한 그리드를 포함한 출시 가능 품질의 완성을 요청했다.

이 문서는 기존 내부 테스트 후보에서 확인된 한계를 고치고 실제 출시판을 만드는 현재 계약이다.
과거 세 장 캠페인과 두 검증용 장면은 회귀와 개발 이력으로 보존하지만, 새 출시판의 규칙이나
사용자 문구를 소유하지 않는다.

## 1. 왜 부분 수정이 아닌 재구축인가

현재 내부 후보는 다음 질문을 검증하는 데는 성공했다.

- 지도에서 설비를 직접 놓고 선로를 완공할 수 있는가?
- 서비스 범위와 실제 전력 공급을 구분할 수 있는가?
- 병원 이중회선, 공장 증설, 예방정비와 폭염 결과를 계산할 수 있는가?
- Title, 저장·재개와 내부 macOS 패키지가 동작하는가?

그러나 출시판으로는 세 가지 구조적 한계가 있다.

1. 선로 하나를 출발점부터 도착점까지 이어지는 순서 목록으로 저장한다. 따라서 전신주나
   변전소에서 세 갈래 이상 분기하거나, 두 경로가 하나로 합쳐지고, 공유 구간의 사용량을 합산하는
   망을 표현할 수 없다.
2. 화면 문구가 기능 이름, 기계 식별자와 검증 용어를 노출한다. 자연스러운 한국어 안내와 이야기
   대신 개발 상태를 읽게 만든다.
3. 세 장이 하나의 실제 캠페인이라기보다 시스템을 차례로 시연하는 긴 튜토리얼에 가깝다.

출시판은 이 세 한계를 그대로 가진 기존 `ProductSession`, `ProductMain`과
`FirstLightMapView`를 범용화하지 않는다. 새 규칙·데이터·기본 장면을 작게 만들고, 과거 경로는
동결 회귀로만 유지한다.

## 2. 완성 목표

플레이어는 가상의 지방도시 **청류시** 전력운영센터의 신임 운영책임자다. 노후한 방사형 배전망을
이어받아 주거지 성장, 병원 증축, 산업단지, 회랑 사고와 기록적인 폭염을 차례로 통과한다.

완성된 게임은 다음 경험을 하나의 저장 가능한 캠페인으로 제공한다.

- 33×21의 촘촘한 지도에서 전신주와 변전소를 놓고 원하는 기존 접속점끼리 선로를 잇는다.
- 한 접속점에서 여러 선로가 분기되고, 서로 다른 경로가 다른 접속점에서 합류한다.
- 발전원, 전신주, 선로와 변전소의 현재 사용량·정격·남은 여유를 보고 망을 보강한다.
- 평상시 공급뿐 아니라 이름 붙은 설비 하나가 끊겼을 때의 우회 공급을 확인한다.
- 프롤로그 세 임무와 본편 다섯 장에서 이전에 만든 망, 운영 자금과 선택의 결과를 이어 간다.
- 장의 시작·사건·결과를 자연스러운 한국어로 이해하고 마지막 에필로그까지 도달한다.
- Title, 저장·재개, 장 재시작, 설정, 도움말과 macOS 패키지를 출시판 경로에서 사용한다.

## 3. 현실성의 범위

출시판은 **22.9 kV급 지역 배전망의 계획 모델**이다. 플레이어가 판단해야 하는 현실 요소는
연결, 설비 정격, 공유 구간 부하, 여유용량, 고장 시 우회와 공사비다.

다음은 의도적으로 계산하지 않는다.

- 교류 전력조류, 위상각, 무효전력과 전압 강하
- 상별 불평형, 단락전류, 보호계전 협조와 차단기 정정
- 도체 장력, 지중 케이블 열해석, 상세 변압기 탭과 전력품질
- 실시간 급전 조작이나 확률 고장

UI는 이 모델을 `정격 안에서 공급 가능한 계획 결과`라고 설명한다. 실제 전력망의 안전 검토나
설계를 대체한다고 표현하지 않는다.

## 4. 분기·합류 가능한 망

### 4.1 그래프

완공된 전력망은 **접속점(node)** 과 **선로 구간(edge)** 으로 저장한다. 선로 전체를 하나의
순서 목록으로 저장하지 않는다.

- 고정 발전 접속점: 전원을 공급한다.
- 전신주: 선로를 꺾거나 분기·합류한다.
- 배전 변전소: 상위망 전력을 수요처 연결 가능 구역에 전달한다.
- 수요 접속점: 병원·산업시설처럼 전용 연결이 필요한 부하를 나타낸다.

공간에서 선이 교차해도 같은 접속점을 공유하지 않으면 전기적으로 연결되지 않는다. 계획 중인
설비는 견적과 예상 결과에는 나타나지만 완공되기 전에는 공급 계산에 참여하지 않는다.

### 4.2 설비 한도

설비 형식마다 필요한 한도만 데이터에서 소유한다.

- 전신주 형식: `maxConnections`, `throughputKw`, 비용과 공사기간
- 선로 형식: `ratingKw`, `maxSpanCells`, 거리당 비용과 공사기간
- 변전소 형식: `maxConnections`, `transformerRatingKw`, `serviceRadiusCells`, 비용과 공사기간
- 발전원: 접속 node와 `capacityKw`, authored 운전순서

출시판 최소 형식은 다음과 같다.

| 설비 | 역할 | 최소 연결 특성 |
|---|---|---|
| 일반 전신주 | 값싼 직선·소규모 분기 | 최대 3개 구간 |
| 보강 전신주 | 큰 분기점·합류점 | 최대 4개 구간, 더 큰 통과용량 |
| 소형 배전 변전소 | 주거지·소규모 중요시설 공급 | 상위선 여러 개와 서비스 용량 |
| 대형 배전 변전소 | 병원·산업단지와 주간선 결절 | 더 많은 접속과 큰 서비스 용량 |
| 일반 배전선 | 값싼 말단·소부하 연결 | 낮은 정격 |
| 보강 배전선 | 공유 주간선·중요 우회선 | 높은 정격과 높은 비용 |

정확한 수치와 형식 식별자는 출시판 world 데이터 한 곳만 소유한다. 문서 표는 의미만 소유한다.

### 4.3 공급 계산

계산은 매 평가 경계에서 처음부터 결정론적으로 다시 수행한다.

1. 완공·사용 가능한 발전원, 접속점과 선로만 후보로 둔다.
2. 수요 묶음을 `(우선순위, loadId)` 순서로 처리한다. 우선순위는
   `생명 유지 → 필수 서비스 → 주거·상업 → 산업`이다.
3. 발전원은 `(dispatchOrder, sourceId)` 순서로 본다. 한 발전원에서 수요 전량을 수용할 수 있는
   **단순 경로** 중 전체 정수 길이가 가장 짧은 경로를 고르고, 동률이면 구간 수와 경로를 이루는
   edge ID 열의 사전식 순서를 사용한다. edge 정수 길이는
   `ceil(sqrt(dx²+dy²) × 1000)`이고 경로 길이는 그 합이다.
4. 수요 묶음 하나는 한 경로로 전량 공급하거나 미공급한다. 큰 수요처의 중요 부분을 따로 지키고
   싶으면 데이터에서 여러 수요 묶음으로 나눈다.
5. 선택한 경로의 발전원, 선로, 전신주와 변전소 용량을 예약한다. 뒤에 처리하는 부하는 남은
   용량만 사용한다.
6. 현재 사용량과 여유율은 경로의 자격을 판정할 뿐, 이미 자격을 갖춘 경로 사이의 선호도를
   바꾸지 않는다. 공급 가능한 경로가 없으면 같은 순서의 최단 위상 경로에서 발전원부터
   수요처 방향으로 처음 만나는 용량 부족 설비를 원인으로 반환한다. 위상 경로 자체가 없으면
   `연결되지 않음`을 반환한다.

주거지처럼 서비스 구역으로 연결되는 부하는 후보 변전소 node를 경로 끝으로 사용한다. 부하
위치가 변전소의 닫힌 서비스 반경 안에 있어야 하며, 선택 경로는 변전소 변압기 용량을 부하량만큼
한 번 예약한다. 후보가 여러 개면 위와 같은 경로 순서 뒤 변전소 ID로 결정한다. 병원처럼 전용
접속점을 가진 부하는 해당 node가 경로 끝이다.

이 방식은 분기와 합류, 공유 주간선의 합산 부하, 여러 발전원과 우회 경로를 지원하지만 물리적인
교류 전력조류를 흉내 내지는 않는다. UI는 각 설비에 `현재 사용 / 정격`과 첫 공급 실패 원인을
보여준다. 정격을 넘기는 상태를 허용한 뒤 경고하는 대신, 넘으면 해당 수요를 공급하지 않는다.

### 4.4 사고와 신뢰도

이름 붙은 사고는 특정 접속점·선로 또는 공간 위험구역에 닿은 설비를 일시적으로 제외한 뒤 같은
공급 계산을 다시 실행한다. 위험구역은 닫힌 polygon이며 내부나 경계 위의 node, 경계 또는 내부와
교차하는 **개별 edge**를 제외한다. 같은 공사나 회로의 다른 edge까지 자동으로 제외하지 않는다.
전기 설비 하나 제거와 여러 설비를 함께 끊는 공간 사고를 서로 다른 결과로 표시한다. 병원의 생명
유지 전력처럼 명시된 필수 부하는 사고 중에도 공급되어야 장을 성공할 수 있다.

## 5. 더 촘촘한 지도

- 권위 격자는 `x=0..32`, `y=0..20`의 33×21 정수 격자다.
- 현재 21×13 prototype보다 배치 선택지를 약 2.5배로 늘리되, 1280×720에서도 각 격자점을
  안정적으로 가리킬 수 있는 간격을 유지한다. 새 지도는 별도 좌표 권위를 가지며 옛 좌표를
  기계적으로 확대하지 않는다.
- 작은 격자선은 낮은 대비, 4칸 단위 주격자선은 높은 대비로 그린다. 좌표 표시는 주격자에만 둔다.
- 포인터와 키보드는 한 칸씩 이동하고, `Shift+방향키`는 네 칸씩 이동한다.
- 화면 확대 없이 1280×720에서 전체 지도를 볼 수 있어야 한다. 확대·이동은 실제 가독성 문제가
  남을 때만 별도 승인한다.
- 강, 도로, 주거지와 위험구역은 격자를 가리지 않으며, 건설 가능 여부는 색뿐 아니라 패턴과
  미리보기 문장으로도 알린다.

## 6. 건설 상호작용

출시판의 건설은 세 도구만 사용한다.

1. **설비 놓기**: 변전소처럼 독립된 설비를 고르고 빈 격자에 계획을 놓는다.
2. **선로 잇기**: 접속 여유가 있는 완공 접속점에서 시작해 빈 격자에 중간 전신주를 순서대로
   놓고 다른 완공 접속점에서 끝낸다. 이미 연결된 전신주나 변전소를 시작·끝으로 다시 골라 새
   분기 또는 합류를 만들 수 있다. 한 공사 계획 자체는 단순한 한 경로로 유지한다.
3. **계획 되돌리기**: 독립 설비 계획은 취소할 수 있다. 선로는 마지막에 놓은 전신주만
   되돌리거나 현재 선로 계획 전체를 취소한다. 중간 구간만 잘라 뒤쪽 계획을 남기지 않는다.

오른쪽 작업 패널은 선택 대상의 사람용 이름, 현재 사용량, 정격, 접속 수, 비용, 공사기간과 첫
실패 이유를 보여준다. 발주 시 이번 계획 전체의 비용과 완공일을 확인하고, 완공 경계까지 진행하면
모든 설비가 한꺼번에 사용 가능해진다. 자동 배선, 추천 경로, 범용 편집기와 완공 자산의 부분
철거는 처음부터 만들지 않는다. 장 시작 시점 재시작으로 잘못된 완공 계획을 복구한다.

인접 접속점 사이 거리 판정은 제곱 유클리드 거리 `dx²+dy²`와 선로 형식의
`maxSpanCells²`를 비교한다. 경계값은 허용하고, 넘으면 해당 계획을 발주할 수 없다.

## 7. 캠페인과 이야기

기존 세 장은 규칙 검증용 **프롤로그 세 임무**로 다시 쓰고 짧게 다듬는다. 그 뒤 같은 청류시
지도와 망을 이어 쓰는 본편 다섯 장을 제공한다. 전체 플레이 시간 목표는 약 3~4시간이다.

| 장 | 이야기와 실제 플레이 결과 |
|---|---|
| 프롤로그 1 `첫 불빛` | 신임 운영책임자가 마을에 첫 전력을 공급한다. 변전소, 선로와 완공 전 무전압을 짧게 익힌다. |
| 프롤로그 2 `두 번째 심장` | 청류의료원의 주·예비 회선을 만든다. 전기적 이중화와 같은 위험구역을 공유하는 두 선의 차이를 익힌다. |
| 프롤로그 3 `열돔 아래` | 공장 증설에 맞춰 발전소를 접속하고 노후설비를 정비한다. 용량과 예고된 위기를 익힌 뒤 본편으로 넘어간다. |
| 1장 `북안 확장` | 새 주거지와 정수장을 하나의 주간선에서 분기한다. 전신주의 접속 수와 공유 구간 정격을 처음 관리한다. |
| 2장 `공유 구간` | 공장 증산과 물류단지가 같은 간선·분기점·변전소 용량을 경쟁한다. 짧은 공유 경로를 보강할지 남쪽 독립 경로를 만들지 결정한다. |
| 3장 `범람 예보` | 저지대 회랑이 함께 끊기기 전에 고지대 우회선을 만들고 기존 망에 다시 합류시킨다. 병원과 정수장의 필수 공급을 지킨다. |
| 4장 `계획 정지` | 서부 전원을 계획정비로 끄기 전에 남부 연계점을 연결한다. 두 전원이 합류하는 망의 선로·분기점·변전소 합산 용량을 관리한다. |
| 5장 `청류 비상전력` | 최대수요와 설비 사용불가가 겹친다. 새 규칙 없이 분기·합류·용량·우회·정비를 종합해 도시를 지킨다. |

장마다 이야기 전달은 세 지점으로 제한한다.

- 시작 브리핑: 누가 무엇을 필요로 하고 왜 지금 해결해야 하는가
- 사건 알림: 어떤 상황이 바뀌었고 누구에게 어떤 영향이 생겼는가
- 결과 보고: 무엇을 지켰고 어떤 선택이 다음 장에 남는가

반복 인물은 운영센터장, 계통운영관, 병원 시설책임자, 재난대응관 네 명을 넘기지 않는다. 대화
선택지, 호감도, 컷신, 음성과 장문의 설정집은 만들지 않는다. 이전 장의 실제 설비·자금·선택에
따라 결과 문장과 다음 브리핑 일부가 달라질 수 있지만 별도 분기 스토리 엔진을 만들지는 않는다.

각 장은 필수 공급·안전 목표와 1~2개의 선택 성과를 가진다. 선택 성과는 별점이나 합산 점수가
아니라 `운영 자금`, `예비용량`, `사고 후 공급 유지`처럼 실제 상태로 남는다. 장 시작 시 고정
투자예산을 추가해 이전 장의 비효율적인 성공이 다음 장을 영구적으로 막지 않게 한다.

## 8. 출시 한국어와 정보 위계

사용자 화면은 `상황 → 영향 또는 이유 → 다음 행동` 순서로 쓴다.

- 직접 안내는 `~하세요`, 상태·결과는 짧은 평서문으로 통일한다.
- 버튼은 `대상 + 동작`으로 쓴다. 예: `전신주 놓기`, `선로 잇기`, `공사 발주`.
- `support`, `span`, `terminal`, `utility`, `feeder`, `merit order`, `LostSales` 같은 내부 영문을
  표시하지 않는다.
- 기계 식별자, enum 이름, 오류 코드와 원시 예외를 표시하지 않는다.
- `3.700 M` 대신 `운영 자금 370만`, `1,845분` 대신 `2일차 06:45`처럼 의미를 붙인다.
- 결과 화면은 `임무 결과 → 공급 결과 → 원인 → 자금 변화 → 세부 설비` 순서다.
- 전문어가 꼭 필요하면 첫 노출에 쉬운 풀이를 붙이고 이후 같은 한국어 용어만 쓴다.

한 개의 출시판 한국어 표현 모듈이 상태명, 오류 설명, 숫자·날짜 형식과 공통 버튼 문구를 소유한다.
장별 브리핑·사건·결과는 캠페인 데이터가 소유한다. 규칙 코드와 화면 곳곳에 같은 문구를 복사하지
않는다.

## 9. 데이터와 코드 경계

출시판의 최종 단일 권위는 다음 두 데이터 파일이다.

- `data/release-world-v1.json`: 지도, 지형, 고정 위치, 설비 형식, 비용·시간·정격과 초기 망
- `data/release-campaign-v1.json`: 프롤로그 세 임무와 본편 다섯 장의 순서, 이야기 문구,
  수요·사건·예산과 완료조건

현재 1단계는 world schema와 그 loader만 만든다. campaign schema와 loader는 실제 장 데이터가
필요한 3단계까지 만들지 않는다.

검사용 정답 경로와 추천 좌표는 런타임 데이터에 넣지 않는다. 자동검사가 자체 witness를 가진다.

새 구현은 다음 경계를 사용한다.

```text
src/Gridworks.Core/Release/       그래프, 공급·용량, 캠페인 상태와 저장
game/ReleaseMain.tscn             출시판 유일 기본 진입 장면
game/Release*.cs/.tscn            지도, 작업 패널, 이야기 카드와 shell
tools/Gridworks.ReleaseChecks/    출시판 독립 결정론 검사
data/release-*.json               출시판 machine authority
```

기존 `src/Gridworks.Core/Product`, `ProductMain`, prototype 장면과 product fixture는 수정해 새 규칙을
끼워 넣지 않는다. 출시판 패키지는 새 기본 장면과 필요한 리소스만 포함하고 prototype 장면은
제외한다.

출시판 저장은 `campaign-save.v2`와 새 콘텐츠 호환 버전을 사용한다. 기존 내부 후보의 v1 저장은
경로 구조와 장 의미가 달라 새 캠페인으로 재생하지 않는다. 최초 실행에서 원본을 `.bak`으로
보존하고 “이전 내부 테스트 기록은 새 출시판과 호환되지 않습니다”라고 설명한 뒤 새 게임을
제공한다. 공개 출시 전 개발 저장을 위한 범용 migration framework는 만들지 않는다. 화면·음량
설정 v2는 그대로 재사용한다.

## 10. 실행 순서

전체 목표는 사용자 요청으로 승인됐지만 구현은 한 번에 다음 한 단계만 진행한다.

### 1단계 — 분기형 배전망 기초 — 완료

- world schema와 strict loader
- 접속점·선로 그래프, 접속 수·정격·남은 용량
- 결정론적 공급 경로와 사고 재계산
- 33×21 좌표, 대표 분기·합류·병목·우회 자동검사

이 단계는 Game 기본 장면을 바꾸지 않는다.

### 2단계 — 출시판 지도와 건설 UX — 완료

- 새 `ReleaseMain`과 촘촘한 지도
- 설비 놓기·취소, 선로 잇기·마지막 전신주 되돌리기·선로 계획 전체 취소·공사 발주
- 선택 설비 사용량·정격·접속 수와 공급 원인 표시
- 전문 한국어 표현 모듈, 장 시작·사건·결과 카드

### 3단계 — 프롤로그·본편 캠페인 — 현재 활성

- 프롤로그 세 임무와 본편 다섯 장 데이터·목표·사건·예산
- 장 사이 자산·자금 carry-over, 실패와 장 재시작
- 출시판 저장·재개와 마지막 에필로그
- 여러 유효 해법과 복구 불가능 상태 부재 검산

### 4단계 — 출시 마감

- 원본 2D 아트·상태 표현·사운드와 화면 정보 위계 마감
- 한국어 전체 문구 감사와 소유자 전체 플레이 반영
- 접근성, 두 해상도, 저장·재개, 전체 캠페인과 package 검증
- macOS 서명·공증 가능 여부, 설치 안내·라이선스·변경 기록 확정

한 단계가 끝날 때 코드·데이터·문서·증거를 커밋하고 독립 검토한 뒤 다음 단계로 전환한다. 같은
검사를 근거 없이 여러 번 반복하거나 LLM 플레이를 단계별 기본 gate로 사용하지 않는다.

## 11. 1단계 완료조건

1. strict loader가 알 수 없는 필드, 중복 식별자·좌표, 끊긴 참조, 잘못된 정격·접속 수와 범위를
   거부한다.
2. 전신주 하나에서 세 갈래로 분기되고 다른 접속점에서 두 경로가 합류하는 대표망이 계산된다.
3. 공유 주간선, 전신주와 변전소의 사용량이 연결된 부하의 합과 일치하며 정격을 넘지 않는다.
4. 같은 망·명령은 항상 같은 공급 경로·사용량·첫 실패 원인을 만든다.
5. 접속 수 초과, 거리 초과, 교차만 한 선의 비접속, 용량 부족과 사용불가 사고를 대표 사례로
   검사한다.
6. 기존 제품·prototype 회귀와 Game build가 깨지지 않는다.
7. 현재 상태 문서와 체크리스트를 갱신하고 한 번의 독립 검토에서 P0/P1이 없다.

### 11.1 구현·검사 기록

1단계는 출시판 전용 Core 경로와 데이터만 추가했으며 기존 Game 기본 장면과 과거 제품 규칙은
수정하지 않았다.

- `data/release-world-v1.json`: 33×21 청류시 대표망과 설비 형식의 단일 machine authority
- `src/Gridworks.Core/Release/`: strict loader, 불변 계약, 결정론적 공급·사고 평가기
- `tools/Gridworks.ReleaseChecks/`: 분기·합류·경계·병목·우회·불변성 9개 검사 묶음
- 출시판 검사: 9 suites / 152 assertions 통과
- 과거 회귀: Scope 0B 3,098 assertions, Scope 1 646 assertions, 누적 Product 검사 통과
- Core·Game build: warning 0 / error 0
- world SHA-256: `92efadd41b1ec91302d75fe606eb46fe50c368e331da72ec5b1eef58953667d1`

독립 검토에서 제기된 서비스 변전소 미건설 상태, 계획 선로 접속 수와 미사용 회로 필드 문제를
단순화해 닫았고, 재검토 결과 P0/P1은 0이다. 1단계는 완료됐다.

## 12. 2단계 완료조건

1. 변전소 계획은 빈 격자에 놓기·옮기기·취소·발주·원자 완공이 가능하고, 선로 계획은 완공
   접속점에서 시작해 중간 전신주를 놓고 다른 완공 접속점에서 끝낼 수 있다.
2. 선로의 마지막 전신주 되돌리기와 계획 전체 취소가 동작하며, 거부된 명령은 시각·망 상태를
   바꾸지 않는다.
3. 거리, 위치 충돌, 접속 수와 설비 형식 한도를 Core가 판정하고, 견적의 비용·공사기간과 완공 뒤
   공급·사용량이 같은 규칙에서 나온다.
4. 명시적으로 실행하는 `ReleaseMain`이 33×21 전체 지도를 1280×720에 표시하고, 마우스와
   방향키·`Shift+방향키`로 같은 격자점을 선택한다.
5. 화면은 사람용 설비 이름, `현재 사용 / 정격`, 접속 수, 비용·공사기간과 첫 실패 이유를
   `상황 → 영향·이유 → 다음 행동` 순서의 자연스러운 한국어로 보여준다. 기계 식별자·enum·원시
   예외를 노출하지 않는다.
6. 실제 viewport 입력과 표준 버튼을 거치는 대표 변전소·분기·합류 공사 흐름을 한 번 확인하고,
   간결한 Core 검사·Game build와 독립 P0/P1 검토를 닫는다.
7. 이 단계에서는 기본 실행 장면을 교체하거나 캠페인 schema·저장·본편 사건을 미리 만들지 않는다.

### 12.1 구현·검사 기록

2단계는 기존 기본 장면을 유지한 채 출시판 전용 건설 화면을 별도 장면으로 추가했다.

- `ReleaseConstructionSession`: 변전소와 선로 계획, 견적, 발주, 원자 완공
- `ReleaseMain`: 33×21 지도, 마우스·키보드 입력, 작업 패널과 짧은 이야기 카드
- 출시판 검사: 12 suites / 217 assertions 통과
- Game Debug build: warning 0 / error 0
- 1280×720 대표 실행: 실제 지도 입력과 표준 버튼으로 변전소 완공 뒤 남부 분기점과 동부
  변전소를 잇는 보강선 완공, 분기점 4연결·변전소 2연결 확인
- world SHA-256: `92efadd41b1ec91302d75fe606eb46fe50c368e331da72ec5b1eef58953667d1`

독립 검토에서 공개 snapshot 변조와 마우스·키보드 혼합 선택 문제를 확인했다. 공개 collection을
읽기 전용으로 바꾸고 키보드 격자점에서 hover 대상을 다시 계산한 뒤 같은 대표 실행과 검사를
통과했으며, 재검토 결과 P0/P1은 0이다. 2단계는 완료됐다.

## 13. 3단계 완료조건

1. `data/release-campaign-v1.json` 한 곳이 프롤로그 세 임무와 본편 다섯 장의 순서, 자연스러운
   한국어 브리핑·사건·결과, 장별 투자예산, 활성 수요·수요 변화, 사고 조건과 목표를 소유한다.
2. 새 캠페인은 고정 접속점은 유지하되 authored 초기 선로만 가진 망에서 시작한다. 플레이어가
   만든 변전소·전신주·선로, 현재 시각과 남은 자금은 마지막 장까지 이어진다.
3. 장 완료 판정은 정상 상태와 해당 장의 고정 사고 상태에서 요구 수요가 전량 공급되는지,
   필요한 분기 접속 수가 충족되는지만 Core에서 확인한다. 점수·별·자동 추천·범용 목표 언어는
   만들지 않는다.
4. 각 장 시작에 투자예산을 더하고 발주 때 실제 견적을 차감한다. 자금 부족 발주는 상태를 바꾸지
   않으며, 비효율적인 성공이 다음 장을 영구적으로 막지 않도록 authored 예산을 검산한다.
5. `ReleaseCampaignRun`만 건설 세션을 변경한다. accepted 명령 기록을 처음부터 결정론적으로
   재실행해 저장을 복원하고, 장 재시작은 현재 장 시작 기록까지만 남긴 뒤 같은 방식으로 복원한다.
6. 저장은 캠페인·world SHA-256과 닫힌 명령 목록만 기록한다. 손상·알 수 없는 버전·다른 콘텐츠는
   기존 파일을 보존한 채 이어하기만 막고 새 게임은 항상 허용한다. 파일 교체는 같은 폴더의 임시
   파일을 flush한 뒤 원자 교체한다.
7. 출시판 Title·Pause에서 새 게임, 이어하기, 저장하고 타이틀로, 현재 장 재시작, 도움말과 기존
   화면·음량 설정을 사용할 수 있다. 성공한 명령 뒤에는 한 슬롯을 자동 저장한다.
8. 기본 실행 장면을 `ReleaseMain`으로 바꾸기 전에 새 게임부터 에필로그까지 8개 장의 대표 흐름,
   fresh-process 저장·재개와 한 장 재시작을 1280×720 실제 입력 한 번으로 확인한다.
9. 검증은 캠페인 loader·장 경계·예산·사고·저장 복원의 간결한 누적 검사, Game build, 위 대표
   실행과 한 번의 독립 P0/P1 검토로 제한한다. LLM·사람 관찰과 표현 마감은 4단계에서 수행한다.

## 14. 최종 완료조건

다음을 모두 충족해야 이 사용자 목표를 완료로 표시한다.

- 새 게임부터 에필로그까지 프롤로그 세 임무와 본편 다섯 장을 기본 출시판 장면에서 끝낼 수 있다.
- 전신주·변전소에서 3개 이상 선로가 분기·합류하고, 모든 설비의 사용량·정격·여유가 공급 결과와
  일치한다.
- 33×21 지도에서 마우스·키보드 건설, 발주, 사건 대응, 저장·재개와 장 재시작이 동작한다.
- 정상·실수·실패·저장 오류 경로에 기계 식별자, 오류 코드, 원시 예외나 번역투가 노출되지 않는다.
- 모든 장이 시작 이유, 사건의 사람에게 미치는 영향, 결과와 다음 장의 연결을 전달한다.
- 열린 crash, data loss, softlock, critical과 major가 0이다.
- 누적 자동검사, 대표 native 전체 플레이, 한국어 소유자 검토와 독립 코드·문서 검토를 마친다.
- 저장소 밖 macOS 패키지에서 새 게임, 저장, fresh-process 재개와 전체 캠페인을 확인한다.
- 공개 배포를 주장하려면 Developer ID 서명·공증과 실제 지원 OS 확인까지 끝낸다. 자격증명이나
  외부 배포 권한이 없으면 내부 출시 후보로 정직하게 기록하고 차단 사유를 남긴다.
