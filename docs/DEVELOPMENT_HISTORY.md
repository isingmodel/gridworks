사용한 세부 승인 문구, 반복된 체크포인트와 도구 호출 순서는 제거했다. 압축 전 공개 문서 전체가
필요하면 Git의 `1f8b80826d7ba0c61dc357d56bce668e5d6bc136` 시점에서 복원할 수 있다.

현재 동작은 [Scope 0B 구현 기준](scopes/SCOPE_0B_PLAYABLE.md)과
[Scope 1 구현 기준](scopes/SCOPE_1_INTERACTION.md), 앞으로의 방향은
[2D 완성 로드맵](ROADMAP_2D.md)이 설명한다.

## 1. 카드로 먼저 확인한 것

첫 실험은 코드를 만들기 전에 정적인 네 장의 카드로 다음 세 가지 인과가 읽히는지 확인했다.

1. 변전소 서비스 권역 안에 있어도 발전소까지 통전 경로가 없으면 공급되지 않는다.
2. 전기적으로 다른 회로도 같은 공간 회랑을 쓰면 하나의 공간 사건으로 함께 끊길 수 있다.
3. 병원 소유 UPS·디젤이 환자를 지키는 것과 전력회사가 병원에 전기를 공급·판매하는 것은 다르다.

첫 카드 실험은 실패로 기록했다. 다섯 응답 모두 미공급과 피더 필요성은 알았지만, 서비스 권역이
접속 가능 범위일 뿐이라는 뜻을 명시하지 못했다. 한 응답에는 전기 사고와 공간 사고를 구분하는
두 번째 결손도 있었다.

| 항목 | 첫 결과 |
|---|---:|
| 서비스 권역·공급 | 0 / 5 |
| 전기 사고·공간 사고 | 4 / 5 |
| 병원 내부전원 경계 | 5 / 5 |
| 비용·안전 교환관계 | 5 / 5 |
| 한 응답 안에서 모두 충족 | 0 / 5 |

이 결과를 사후에 완화해 통과시키지 않았다. 대신 숫자, 망 구조와 정답은 그대로 두고 질문을
항목별로 분리한 두 번째 카드 실험을 새로 수행했다. 두 번째 실험은 모든 항목과 통합 설명에서
5/5였다. 이 결과는 표현 구조가 원인 구분을 돕는다는 증거이지 사람의 이해나 재미를 증명하지
않는다.

## 2. 고정 시나리오를 실제 화면으로 옮긴 것

다음 단계에서는 카드의 인과를 Godot 2D 화면과 순수 C# 규칙으로 옮겼다. 플레이어는 마을 피더를
발주하고, 값싼 강변 병렬선과 비싸지만 공간적으로 분리된 북부 우회선 중 하나를 선택한다. 완공 뒤
예고된 강변 회랑 사건을 겪고 서비스와 현금을 결산한다.

이 구현으로 다음을 확인했다.

- 기하학적 서비스 권역과 실제 통전 경로를 별도 상태로 표현할 수 있다.
- 전기 회로 식별자와 공간 위험 그룹을 별도로 적용할 수 있다.
- 공사 중 설비는 공급에 참여하지 않고 완공 경계에서 한 번에 편입된다.
- 병원 내부전원 사용, 전력회사 인도 전력, 판매와 미공급 보상을 따로 보존할 수 있다.
- 화면이 계산을 다시 하지 않고 Core가 반환한 상태만으로 원인과 결산을 보여줄 수 있다.

초기 다섯 실행 방식은 게임 결과가 아니라 증거 절차 때문에 중단됐다. 도구 탐색 순서, 무해한
import 시도, prompt 포장, metadata 원문 보존, 실행 시각과 manifest 같은 규칙이 계속 늘어났고,
실제로 게임을 끝낸 세션도 형식 때문에 무효가 됐다. 마지막 방식은 사용자 정의 runner 체계를
버리고 플랫폼 원본, 앱 진단 기록과 교체 없는 고정 다섯 행만 사용했다.

마지막 다섯 실행은 모두 화면을 끝까지 조작했고 네 이해 항목과 통합 설명이 5/5였다. 다섯 세션이
모두 북부 우회선을 골랐고 `남음/끊김` 선택을 서로 독립된 스위치처럼 보았다는 점은 진단으로만
남겼다. 선택 밸런스나 사람 사용성의 증거로 쓰지 않았다.

핵심 식별값은 다음과 같다.

- fixture SHA-256: `e617f7b9163294ca0e72f89bf3cb3a3be634c0de21f1d2736549863f53617e57`

## 3. 지지물을 직접 놓는 상호작용을 분리한 것

고정 회랑 선택 다음에는 선로 경로를 직접 만드는 가장 작은 상호작용만 떼어 구현했다. source와
target은 고정하고, 플레이어가 정수 격자에 지지물을 순서대로 놓는다. 인접한 모든 구간이 하나의
최대 길이 이하여야 발주할 수 있고, 발주 뒤 공사 중에는 무전압이며 완공 뒤에만 target이 켜진다.

이 구현은 기존 시나리오 전용 Core와 UI를 일반화하지 않고 별도 세션과 장면으로 만들었다. strict
fixture loader, preview와 명령의 동일 판정, 실패 시 상태 불변, 원자 완공, 결정론적 상태 JSON을
자동검사했다. 최종 자동검사는 8개 묶음, 646개 assertion을 통과했다.

공식 LLM 관찰은 한 번 수행했다. LLM 참가자는 `(4,4) → (7,4)`에 지지물을 놓고 완공까지
진행했으며, 모든 연속 구간의 거리 제한과 공사 중 무전압·완공 후 통전을 설명했다. 원래 검토했던
3회 집계는 평가하지 않았고, 사용자가 한 번의 관찰을 충분한 종료 근거로 수용했다. 따라서 이
결과는 한 번의 성공 관찰이지 성공률이나 사람 사용성 증거가 아니다.

- fixture SHA-256: `f308a739f9e4fcaf9d6f07aacba65af6fdd9ae3600a1e5569254fcb749bb2edc`

## 4. 중단하고 되돌린 범위

한 차례 Scope 1을 구현할 권한보다 넓게 해석해 fixture, Core, UI와 검사를 먼저 추가한 적이 있다.
당시 작업은 자동검사와 headless smoke까지만 진행됐고, 독립 source review, native 사전점검과 공식
실행 전 모두 되돌렸다. 이후 사용자의 명시적 승인 아래 같은 범위를 다시 작게 구현했다.

여기서 얻은 원칙은 상세한 후보 문서가 곧 구현 권한은 아니라는 것이다. 앞으로도 로드맵은 방향을
설명할 뿐이며, 한 단계의 활성화는 별도 사용자 결정으로만 이뤄진다.

## 5. 앞으로 유지할 교훈

### 규칙과 데이터

- 한 단계에서는 한 가지 가장 큰 위험만 연다.
- 실행 숫자는 한 개의 machine-readable fixture가 소유하고 문서·장면·검사에 복제하지 않는다.
- UI는 규칙을 다시 계산하지 않고 Core의 preview와 상태를 표현한다.
- 거부된 명령은 상태와 현금을 바꾸지 않으며 발주·완공은 경계에서 원자적으로 바뀐다. 철거를
  나중에 열더라도 같은 원칙을 따른다.
- 현재 전용 프로토타입의 가정을 범용 제품 모델로 승격하지 않는다.

### 증거

- schema, 보존식, 상태전이, crash와 save 손상처럼 기계적인 사실만 강한 PASS/FAIL로 다룬다.
- 사람의 이해·혼란·재미는 `확인됨 / 문제 관찰 / 미관찰`로 기록하고 비율 하나로 숨기지 않는다.
- 실패한 결과를 사후 재채점하거나, 불리한 세션을 교체해 통과율을 만들지 않는다.
- 제품 실패와 증거 수집 실패를 구분하되, 증거 체계 자체를 제품보다 복잡하게 만들지 않는다.
- LLM 플레이는 자동검사가 답하지 못하는 한 문장짜리 상호작용 질문이 남을 때만 최대 한 번
  사용한다. 사람 검증이나 출시 증거로 세지 않는다.

### 주장 상한

이 내부 후보 종료 시점까지 `HumanValidationStatus = NOT_COLLECTED`였다. 기존 결과는 정해진
화면에서 같은 계열의 LLM이 과제를 수행하고 설명했다는 것만 지지한다. 사람 사용성, 재미,
접근성, 밸런스, 전략 다양성이나 일반적인 전력망 시뮬레이션의 정확성을 증명하지 않는다.

## 6. 소유자 전체 플레이와 출시판 재구축

2026-08-17 프로젝트 소유자가 내부 후보를 처음부터 끝까지 직접 플레이했다. 기능을 끝낼 수
있다는 사실과 출시 품질은 별개였고, 다음 문제가 출시 차단 수준으로 확인됐다.

- 개발 용어, 기계 식별자, 혼합 영문과 번역투가 화면에 노출돼 전문적인 제품처럼 읽히지 않았다.
- 전신주가 한 선로 안의 경유점이라 두 구간보다 많이 연결할 수 없고, 일반적인 분기·합류와 공유
  설비 용량을 다룰 수 없었다.
- 세 장에는 일관된 인물·갈등·결과가 부족해 실제 본편보다 긴 튜토리얼에 가까웠다.
- 지도가 성겨 경로 선택의 공간적 차이가 작았다.

이 검토로 기존 2D 패키지는 출시판이 아니라 역사적 내부 후보로 격하됐다. 새 목표는 분기형
배전망 Core, 촘촘한 지도, 전문 한국어, 프롤로그 세 임무와 본편 다섯 장을 가진 새 기본 제품
경로를 완성하는 것이다. 소유자 검토는 실제 사람의 직접 사용 증거지만 외부 사용자 테스트나
일반적인 사용성 결론은 아니므로 `OwnerPlayReviewStatus = COLLECTED`,
`ExternalHumanValidationStatus = NOT_COLLECTED`로 구분한다.
