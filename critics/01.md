# 2. Scope 0의 수치는 맞지만, 핵심 가설과 맞지 않는다

Scope 0은 다음 선택을 제공합니다.

| 선택 |  건설비 | 공기 | 사고 결과                       |
| -- | ---: | -: | --------------------------- |
| A  |  8 M | 2일 | E1과 같은 `OLD_BAY` 고장으로 함께 제거 |
| B  | 12 M | 3일 | 별도 경계라 병원 계통공급 유지           |

사고는 정확히 4시간이고, 병원 내부 UPS·디젤도 정확히 4시간을 버팁니다. 따라서 A와 B 모두 병원 P0 미공급은 0입니다. A는 내부전원을 완전히 소진하고, B는 내부전원을 쓰지 않습니다.

문서의 oracle을 다시 계산하면 다음과 같습니다.

| 항목              |         A |          B |
| --------------- | --------: | ---------: |
| 추가 건설비          |       8 M |       12 M |
| 사고 중 전력회사 병원 공급 |     0 MWh |     32 MWh |
| 병원 P0 미공급       |     0 MWh |      0 MWh |
| 내부 비상전원 잔여      |        0분 |        미사용 |
| 사고 현금변화         | -0.7168 M | -0.07472 M |
| 기말 현금           | 5.71168 M |  2.35376 M |

B는 사고 손실을 A보다 `0.64208 M` 줄입니다.

```text
0.7168 - 0.07472 = 0.64208 M
```

하지만 B의 건설비는 `4 M` 더 비쌉니다.

```text
12 - 8 = 4 M
```

결과적으로 B는 A보다 기말 현금을 `3.35792 M` 덜 남깁니다.

```text
5.71168 - 2.35376 = 3.35792 M
```

문서의 공식 제품 목표는 다음 순서입니다.

1. 안전 조건 통과
2. 기말 현금 최대화

A와 B 모두 P0 미공급 0으로 안전조건을 통과하므로, **현재 한 개의 고정 시나리오에서는 A가 공식 목표상 명백한 정답**입니다.

B가 제공하는 것은 다음 두 가지입니다.

* 전력회사의 병원 공급 연속성
* 내부 비상전원을 소진하지 않는 추가 여유

하지만 어느 것도 현재 Scope 0의 안전 게이트나 기말 현금 평가에서 B의 4 M 추가비용을 정당화하지 못합니다.

## 2.1 A는 이 fixture에서 실제 기능도 거의 없다

A는 병원 예비선이지만 다음과 같습니다.

* 정상 상태에서는 기존 E1이 32 MW 전체 수요를 감당합니다.
* 사고에서는 E1과 함께 제거됩니다.
* 다른 선로 사고는 Scope 0에 없습니다.
* A를 짓지 않는 선택은 허용되지 않습니다.

즉, 현재 fixture에서 A의 실질적인 역할은 **“두 번째 선이 있어도 같은 상위 경계를 공유하면 무용지물”이라는 사실을 보여주는 것**입니다.

이것은 훌륭한 튜토리얼 소재입니다. 그러나 전략적 대안이라기보다는 오답 선택지에 가깝습니다.

# 3. Scope 0의 목적을 둘 중 하나로 확정해야 한다

현재 문서는 Scope 0이 다음을 동시에 검증한다고 말합니다.

* 공통 고장 경계를 이해하는가
* A와 B 사이에서 실제로 고민하는가
* 선택이 재미있는가

현재 fixture는 첫 번째 질문에는 적합하지만, 두 번째와 세 번째에는 적합하지 않습니다.

## 권장안 A: 이해도 검증판으로 명확히 규정

가장 단순하고 권장하는 방향입니다.

Scope 0의 한 문장을 다음처럼 바꿉니다.

> 플레이어는 서비스 범위와 실제 전기 연결을 구분하고, 두 선로가 같은 상위 고장 경계를 공유하면 동시에 끊긴다는 사실을 사고 전후에 설명할 수 있는가?

그에 따라 다음을 수정합니다.

* “A와 B 사이의 실제 고민”이라는 표현 제거
* “재미 검증”보다 “핵심 인과 이해와 선택의 소유감 검증”으로 축소
* A/B 선택 비율은 통과조건에서 제외
* 사고 전에 결과를 예측하게 함
* 사고 뒤 예측과 실제 결과의 차이를 기록
* 현금 차이는 사후 설명 자료로만 사용
* B가 경제적으로 균형 잡힌 선택이라고 주장하지 않음

이렇게 하면 현재 fixture를 거의 그대로 유지할 수 있습니다.

## 대안 B: 실제 전략적 trade-off를 검증

이 경우 fixture를 바꿔야 합니다. 최소한 다음 중 하나가 필요합니다.

### 방법 1: 사고 지속시간을 선택 시점에 확정적으로 알려주지 않는다

```text
예상 복구시간: 2~6시간
내부 비상전원: 4시간
```

실제 권위 사건은 여전히 고정 4시간이어도 됩니다. 플레이어는 A를 택해 비상전원에 의존할지, B에 보험료를 낼지 고민합니다.

다만 플레이어에게 무엇을 알려주는지 정확하게 고정해야 합니다.

### 방법 2: “A 또는 B” 대신 “내부 비상전원 의존 또는 B”로 비교

기능이 없는 A를 제거하고 다음을 비교합니다.

* 추가 회선 없이 병원 내부전원에 의존
* 12 M을 내고 독립 B 구축

이것이 현재 fixture의 실제 경제적 선택에 더 가깝습니다.

### 방법 3: A가 좁은 사고에는 유효하도록 설계

예를 들어:

* A는 개별 E1 선로 고장에는 살아남음
* A는 `OLD_BAY` 공통원인 사고에는 함께 탈락
* B는 두 사고 모두에서 살아남음

사고 종류가 선택 시점에는 완전히 확정되지 않아야 A와 B가 위험·비용 trade-off가 됩니다.

**현재 단계에서는 권장안 A가 낫습니다.** 전략적 재미를 억지로 증명하려고 Scope 0에 불확실성·복수 사고·새 파라미터를 추가하면 다시 범위가 커집니다.

# 4. 사람 플레이테스트 통과기준에 문제가 있다

현재 기준에는 다음이 포함됩니다.

> 참가자 집단에서 A와 B가 각각 최소 한 번 실제로 선택된다.

이는 통과조건으로 부적절합니다.

모두 A를 선택했다면 다음 가능성이 있습니다.

* A가 경제적으로 합리적이었음
* B의 이점이 설명되지 않았음
* 플레이어가 위험을 이해했지만 비상전원을 신뢰했음

모두 B를 선택했다면 다음 가능성이 있습니다.

* `독립 경계`라는 표현이 정답을 직접 암시했음
* 비싼 쪽이 좋은 선택처럼 보였음
* 플레이어가 경제 결과를 이해하지 못했음

어느 쪽도 자동 실패가 아닙니다. 반대로 한 명이 오해해서 A를 선택해도 “양쪽이 선택됐다”는 조건은 충족됩니다.

### 권장 통과기준

기존 선택 비율 조건을 제거하고 다음으로 교체합니다.

1. 선택 전 5명 중 4명 이상이 “OLD_BAY 고장 시 어떤 경로가 남는가”를 정확히 예측한다.
2. 선택 전 5명 중 4명 이상이 병원 내부전원과 전력회사 계통공급을 구분한다.
3. 사고 후 5명 중 4명 이상이 결과를 자신의 경로 선택과 연결한다.
4. A/B 선택 비율과 이유는 **진단 데이터**로만 기록한다.
5. 참가자가 선택한 이유와 예상 결과가 일치하는지 기록한다.

## 4.1 사고 전에 무엇을 알려주는지 고정해야 한다

현재 문서는 다음은 명시합니다.

* 정확한 사고 시각 공개
* 취약 구간 공개
* A/B 비용과 완공일 공개

그러나 다음 정보가 선택 전에 공개되는지는 명확하지 않습니다.

* 사고 지속시간이 정확히 4시간이라는 사실
* `OLD_BAY`가 E1과 A를 모두 제거한다는 사실
* 병원 내부전원이 정확히 4시간이라는 사실
* 내부전원 소진이 후속 위험이나 비용을 만드는지 여부

이 정보 집합이 다르면 A/B 선택의 의미가 완전히 달라집니다.

Scope 0 문서에 다음 표를 추가해야 합니다.

| 정보           | 선택 전에 공개?           |
| ------------ | ------------------- |
| 사고 발생시각      | 예                   |
| 영향받는 고장 경계   | 예 / 아니오 중 확정        |
| 예상 복구시간      | 정확값 / 범위 / 비공개 중 확정 |
| 병원 내부전원 지속시간 | 예                   |
| 내부전원 사용 비용   | 없음                  |
| 사고 후 추가 사건   | 없음                  |

이 표 없이는 플레이테스트 결과를 해석할 수 없습니다.

## 4.2 카드 순서와 용어가 선택을 유도할 수 있다

현재 카드는 대략 다음처럼 표시됩니다.

```text
A · SHARED BOUNDARY
B · INDEPENDENT BOUNDARY
```

`독립`은 긍정적이고 `공통`은 위험한 표현이라, 시스템을 이해하지 못해도 B를 고를 수 있습니다.

보다 중립적인 인과 표현이 적절합니다.

```text
A — 기존 E1과 같은 상위 차단기를 사용
B — 기존 E1과 다른 상위 차단기를 사용
```

그리고 참가자별로 다음을 교차 배치해야 합니다.

* 카드 좌우 순서
* A/B 문자
* 지도상 상·하 위치

비용과 실제 규칙은 유지합니다. 선택 전에 “고장 시 어떤 부하가 어디서 공급될 것인가”를 말하게 해야 합니다.

# 5. 2일과 3일 공기 차이는 현재 아무 효과가 없다

정확한 사고 경고는 `DAY 1 08:00`, 사고는 `DAY 9 16:00`입니다. A는 `DAY 3`, B는 `DAY 4`에 완공됩니다.

* A는 사고 152시간 전에 완공
* B는 사고 128시간 전에 완공

따라서 A의 2일과 B의 3일 공사 차이는 아무 결정에도 영향을 주지 않습니다.

현재 Scope 0은 여러 변수를 동시에 검증하지 않는다는 원칙을 갖고 있습니다. 그렇다면 다음 중 하나가 맞습니다.

* 공기를 동일하게 하여 비용·경계 차이만 검증
* 사고 경고 시점을 조정하여 공기 차이가 실제로 의미 있게 함
* 공기는 정보로 표시하되 이번 테스트에서 의미 없는 fixture임을 명시

**권장안은 A와 B 공기를 같게 하는 것**입니다. Scope 0의 핵심은 공통 경계이지 공정 일정이 아닙니다.

# 6. 마을 후보 셀 두 개도 정의가 부족하다

플레이어는 마을 변전소를 “지정된 두 후보 셀 중 하나”에 놓습니다. 그러나 두 후보가 무엇이 다른지는 정의되지 않았습니다.

차이가 없다면 의미 없는 클릭이고, 차이가 있다면 Scope 0에 설명되지 않은 두 번째 전략 문제가 됩니다.

더구나 마을 접속은 하나의 `StartTownConnectionPackage` 명령으로 변전소와 피더를 함께 건설합니다. 플레이어가 실제로 경험하는 것은 다음입니다.

```text
패키지 발주
→ 하루 후 변전소와 피더가 동시에 완공
→ 서비스 권역 점등
```

그러면 “변전소가 범위 안에 있어도 발전소까지 연결되지 않으면 켜지지 않는다”는 인과를 직접 조작하기 어렵습니다.

### 권장 단순화

의미 없는 두 후보 셀을 제거하고, 두 단계로 나눕니다.

1. 고정 위치에 변전소 배치
2. 발전소 쪽 고정 피더 연결

명령은 한두 개 늘어나지만, 핵심 인과를 직접 보여줍니다.

또는 현재 패키지 명령을 유지하려면 두 후보 셀의 명확한 차이를 문서에 적어야 합니다. 예를 들어 하나는 마을 전체를 덮고 하나는 일부만 덮는다면, 그 자체가 별도의 검증 가설이 됩니다.

---

# 7. Scope 0에서 공사 “대기열”은 실제로 사용되지 않는다

마을 패키지를 완공해야 A/B가 열리므로, Scope 0에서는 동시에 두 공사를 대기열에 올릴 수 없습니다. 취소·재정렬도 없습니다.

따라서 실제 상태는 대기열이 아니라 다음 하나면 충분합니다.

```text
ActiveConstructionJob?
```

지금부터 일반적인 queue 자료구조와 UI를 만들면 미래 1.0 기능을 선구현하는 셈입니다.

### 권장

Scope 0에서는:

```text
ActiveConstructionJob | null
```

만 구현합니다. 여러 프로젝트 발주와 순서 변경이 실제로 열리는 Timeline 게이트에서 queue로 확장합니다.

---

# 8. `AdvanceToNextDecisionMarker()` 이름도 실제 동작과 맞지 않는다

이 명령은 다음 중 가장 가까운 시각으로 이동합니다.

* 공사 완료
* 의무 활성
* 경고
* 사고 시작
* 복구

이 중 공사 완료나 복구는 반드시 플레이어 결정 시점은 아닙니다.

더 정확한 이름은 다음입니다.

```text
AdvanceToNextMilestone()
```

또는:

```text
AdvanceToNextStop()
```

명령이 하는 일과 이름을 맞추는 편이 이후 상태기계 구현을 단순화합니다.

---

# 9. 정수 화폐의 최소단위가 정의되지 않았다

문서와 `AGENTS`는 정수 화폐를 요구하지만 실제 숫자는 다음과 같습니다.

* `0.01248 M`
* `0.7168 M`
* `5.71168 M`

현재 `M`을 어떤 정수 단위로 저장하는지 정해지지 않았습니다.

가장 단순한 계약은 다음입니다.

```text
1 M = 1,000,000 CashUnit
Money = long CashUnit
```

그러면:

```text
0.01248 M = 12,480 CashUnit
0.7168 M  = 716,800 CashUnit
```

단가도 JSON의 부동소수점으로 처리하지 않는 편이 좋습니다.

```text
SaleRateCashPerGWh = 180,000
GasCostCashPerGWh  = 115,000
```

에너지를 `kW·minute`으로 누적한 뒤 정수 나눗셈이 정확히 닫히는 marker만 허용합니다. 문서가 이미 “반올림이 필요하면 fixture를 거부한다”고 규정했으므로, 화폐 단위만 명시하면 됩니다.

---

# 10. 병원 내부전원에는 출력 정격도 필요하다

현재는 UPS 15분, 디젤 3시간 45분이라는 시간만 정의되어 있습니다. 병원 부하는 8 MW입니다.

다음 한 줄을 추가해야 합니다.

```text
UPS와 비상 디젤은 각각 병원 P0 부하 8 MW 전부를 공급할 수 있다.
```

그렇지 않으면 4시간이라는 지속시간만으로는 P0 연속성을 증명할 수 없습니다.

또한 Scope 0과 1.0 후보 사이의 표현도 맞춰야 합니다.

* Scope 0: UPS 포함 총 4시간
* 1.0 후보: UPS 15분 + 비상 디젤 4시간으로 읽힘

후자는 총 4시간 15분인지, 총 4시간인지 명시해야 합니다.

---

# 11. 일반 JSON Schema는 필요 없지만 최소 scenario validator는 필요하다

Scope 0에서 범용 schema registry를 만들지 않는 것은 적절합니다. 하지만 `scenario.json`을 신뢰하고 바로 실행하면 오타 하나가 잘못된 플레이테스트 결과를 만들 수 있습니다.

다음만 검사하는 수동 validator면 충분합니다.

* 모든 ID가 고유함
* 참조하는 자산·경계 ID가 존재함
* 비용·정격·기간이 음수가 아님
* 사건 시작 < 사건 종료
* A는 `OLD_BAY`에 포함되고 B는 포함되지 않음
* A/B 모두 선택 시점 뒤 사고 전 완공 가능
* 병원 내부전원 정격 ≥ 8 MW
* 병원 내부전원 에너지 ≥ 32 MWh
* 판매·발전비·보상 정산이 정수 화폐단위로 닫힘
* 사건 종료와 복구 순서가 한 틱 공백을 만들지 않음

이는 미래 확장용 schema가 아니라 **현재 fixture 자체의 무결성 검사**입니다.

---

# 12. 사람 검증은 “재미”를 아직 측정하지 않는다

현재 사람 기준은 주로 다음을 측정합니다.

* 마을을 켰는가
* 서비스 반경과 연결을 구분하는가
* A/B 안전 차이를 설명하는가
* 사고를 자기 선택과 연결하는가
* 다시 한다면 바꿀 결정을 말하는가

이는 이해도와 인과 귀속을 잘 측정합니다. 하지만 Scope 0의 목적 문구에는 “재미있고 이해 가능한지”가 포함되어 있습니다.

둘 중 하나를 택해야 합니다.

### 더 정직한 권장 표현

> 핵심 인과가 이해 가능하고, 선택 결과를 자신의 결정으로 받아들이는지 검증한다.

“재미” 검증은 다음 게이트로 미룹니다.

### 재미까지 보려면 추가할 관찰

* 종료 후 다른 경로로 자발적으로 다시 플레이하는가
* 후속 시나리오를 플레이하고 싶다고 구체적으로 말하는가
* 단순히 정답을 확인하려는 것이 아니라 다른 설계를 시험하려는가

참가자 5명은 첫 formative test에는 적절하지만, `4/5` 한 번을 제품 가설의 확정적 증명으로 해석해서는 안 됩니다. 첫 라운드의 문제를 수정한 뒤 별도의 신규 참가자 라운드가 필요합니다.

# 13. 오래된 `critics/` 문서는 격리해야 한다

현재 저장소에는 `critics/critic1.md`, `critic2.md`, `critic3.md`가 추가되어 있습니다. 이 문서들은 이전 커밋을 기준으로 작성되어 다음과 같은 낡은 지시를 포함합니다.

* Static Balance Lab부터 구현
* 이전 1.0 범위
* 이전 `AGENTS` 상태
* 이미 수정된 발전소 일정 및 수치 문제

사람은 역사적 리뷰임을 알 수 있지만, Codex 검색이나 문맥 수집 과정에서는 현재 규칙과 함께 노출될 수 있습니다. 문서 크기도 상당합니다.

### 권장

다음 중 하나를 적용합니다.

```text
docs/archive/reviews/
```

로 이동하고 각 파일 상단에 다음을 추가합니다.

```text
Status: historical, non-authoritative
Reviewed commit: 8d8047d
Superseded by: 65905df
Do not use as implementation instructions.
```

또는 저장소에서 제거하고 Git 이력으로만 보존합니다.

# 14. 통합 기획서의 조건부 기능 표현을 더 정리할 필요가 있다

권위 우선순위는 잘 정의되어 있습니다. Scope 0이 최우선이고, `SCOPE_1_0.md`와 후속 문서는 미개방 후보입니다.

그러나 `GAME_DESIGN_KO.md` 본문에는 여전히 다음이 실제 제품 경험처럼 상세하게 서술됩니다.

* 자유 경로
* 배터리와 피커
* DR
* 3장 캠페인
* DC 조류
* 열 모델
* 상세 사고 보고서
* 3D HUD

기술적으로는 “해당 게이트가 열리면”이라는 단서가 많이 추가됐지만, 문서가 매우 길어 Codex가 일부 절만 검색하면 조건을 놓칠 수 있습니다.

### 권장 표현 규칙

각 미개방 절 제목에 상태를 직접 붙입니다.

```text
## 6. 송전선과 철탑 [조건부 1.0 후보]
## 7. 발전·저장 [조건부 1.0 후보]
## 11. 폭염 사건 [조건부 1.0 후보]
## 13. 3D 화면 [조건부 Presentation Gate]
```

그리고 Scope 0에 해당하는 규칙은 별도 표시합니다.

```text
[CURRENT: SCOPE 0]
```

권위 문서를 읽는 사람이 문단의 첫 줄만 보고도 현재 구현 여부를 알 수 있어야 합니다.

# 15. 원전·데이터센터·냉각수 후속 방향

후속 문서는 상당히 개선됐습니다.

* 데이터센터는 외부 사업자의 앵커 계약
* 플레이어는 서버 사업 전체를 소유하지 않음
* 물 권역은 하나
* 수랭·공랭 두 상태
* 거리 효과는 비물리적 물 손실이 아니라 펌프 전력
* 프로젝트 금융 제외
* 원전 입지 부담은 `LOW/HIGH`
* WATER/AIR 전환에 별도 기술트리 없음

다만 세 가지는 다시 단순화하는 편이 좋습니다.

## 15.1 데이터센터에도 `LOW/HIGH` 입지 부담을 적용해야 한다

현재 `LOW/HIGH`는 원전과 향후 열발전 시설에만 적용됩니다. 데이터센터의 지역 수용성은 실질적으로 빠져 있습니다.

사용자가 추가하려던 차별점은 발전소뿐 아니라 **데이터센터의 NIMBY**도 포함합니다.

복잡한 정치 시스템은 필요 없습니다. 데이터센터에도 같은 authored 필드 하나만 사용하면 됩니다.

```text
SitingBurdenTier = LOW | HIGH
```

결과도 동일하게 제한합니다.

```text
HIGH:
  고정 추가 접속·부지 분담금
  고정 허가 지연
```

원인 태그는 설명용으로 하나만 붙일 수 있습니다.

```text
RESIDENTIAL_ADJACENCY
LOCAL_WATER_PRESSURE
```

런타임 수용성 점수, 주민 AI, 시위 확률은 만들지 않습니다.

## 15.2 서비스분율 5% 단위는 미세조작을 만든다

현재 데이터센터 서비스분율은 `0~100%`를 5% 단위로 조정합니다. 이는 21개 상태입니다.

이렇게 하면 플레이어는 폭염 때 65%, 70%, 75%를 반복 비교하며 임계값을 맞추게 됩니다. 원래 목적이었던 단순한 전력–물 선택보다 연속 최적화 문제가 앞에 나옵니다.

다음 2~3개 상태가 낫습니다.

```text
FULL
CURTAILED
OFF
```

또는:

```text
FULL = 100%
REDUCED = authored 고정 비율
```

감축 비율은 계약이 정하고 플레이어가 숫자를 튜닝하지 않습니다.

## 15.3 WATER/AIR 전환을 매 1분 허용하지 않는 편이 좋다

현재는 별도 비용 없이 다음 1분 경계에서 양방향 전환할 수 있습니다.

이는 수요·물 여유가 경계를 오갈 때 매 틱 모드를 바꾸는 현상을 만들 수 있습니다. 전환시간이나 복잡한 설비 모델을 추가할 필요는 없습니다.

단순한 해결책은 다음입니다.

> WATER/AIR 전환은 자동 정지된 자원부족 결정시점 또는 authored 운영 marker에서만 가능하다.

그러면 별도 전환시간·비용 없이도 미세조작을 막을 수 있습니다.

# 16. 수정 후 권장 구현 순서

P0 수정 후에는 현재 Scope 0만 다음 순서로 구현하는 것이 적절합니다.

## 1단계: 저장소 작업 규칙

* `.AGENTS.md` → `AGENTS.md`
* 현재 게이트를 Scope 0로 명시
* 오래된 critics 문서 격리

## 2단계: fixture 계약

* `data/scenario.json`
* 화폐 최소단위
* 병원 비상전원 정격
* 선택 전 공개정보
* 최소 validator

## 3단계: Core oracle부터 구현

Godot보다 먼저 다음 테스트를 통과시킵니다.

* E1 연결 시 병원·마을 공급
* A/B 공통경계 제거
* 내부전원 240분
* 사건 종료 경계 복구
* A/B 사건 cash oracle
* A/B 기말 cash oracle
* 실패 명령의 원자성

## 4단계: 최소 상태기계

* 고정 배치
* 하나의 활성 공사
* 마일스톤 진행
* 의무 활성
* 사고 시작·종료

## 5단계: Godot 2D

* 서비스 권역
* 경로 패턴
* 현금·수요
* `왜?` 패널
* 중립적인 A/B 카드

## 6단계: 플레이테스트

* 카드·지도 위치 counterbalancing
* 선택 전 예측 기록
* 첫 선택만 기록
* 사고 후 설명 기록
* 신규 참가자 5명
* 수정 후 신규 참가자 두 번째 라운드

Static Balance Lab, DC 조류, 자유 배선, 배터리, 3D는 이 결과가 나오기 전에는 열지 않습니다.

# 최종 판정

이번 업데이트로 **개발 계획 자체는 상당히 좋은 상태**가 됐습니다. 특히 “큰 기획서를 순서대로 모두 구현한다”는 방식에서 벗어나, 실제 사람 행동을 본 뒤 다음 축 하나만 여는 구조로 바뀐 것은 정확한 결정입니다.

그러나 현재 Scope 0는 다음 두 문장을 혼동하고 있습니다.

> 플레이어가 공통 고장 경계를 이해하는가?

> 플레이어가 값싼 취약망과 비싼 안전망 사이에서 전략적으로 고민하는가?

현재 fixture는 첫 번째 질문에는 적합합니다. 두 번째 질문에는 부적합합니다. 현재 단일 사건·안전 게이트·기말 현금 기준에서는 **A가 합리적인 선택이고 B는 과잉투자**이기 때문입니다.

따라서 구현 전에 반드시 다음 네 가지를 닫아야 합니다.

1. `.AGENTS.md`를 `AGENTS.md`로 수정
2. Scope 0를 이해도 검증으로 좁힐지, 실제 전략 trade-off로 재설계할지 결정
3. A/B 선택 비율을 통과조건에서 제거하고 사전 예측 중심으로 변경
4. 선택 전에 공개되는 사고정보를 명시

이 네 가지를 수정하면 Scope 0는 **바이브 코딩을 시작하기에 적절할 정도로 작고, 검증 가능하고, 실패했을 때 무엇이 틀렸는지 알 수 있는 계획**이 됩니다.
