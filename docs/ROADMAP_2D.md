# Gridworks — 2D 게임 완성 로드맵

> 문서 상태: 계획

이 문서는 현재의 두 검증용 구현에서 출발해 하나의 완성 가능한 2D 게임에 도달하는 순서를
정한다. 로드맵은 구현 허가나 자동 backlog가 아니다. 한 번에 한 단계만 별도 승인해 열고, 그
단계의 결과를 검토한 뒤 다음 단계를 유지·축소·삭제한다.

현재 활성 단계는 루트 [README](../README.md), 진행 증거는
[로드맵 체크리스트](ROADMAP_2D_CHECKLIST.md), 제품의 안정된 경험 원칙은
[게임 기획서](product/GAME_DESIGN_KO.md)가 소유한다.

## 1. 출발점

현재 저장소에는 서로 다른 질문을 검증한 두 개의 완성된 수직 slice가 있다.

- [강변 병원 회랑](scopes/SCOPE_0B_PLAYABLE.md)은 고정된 마을·병원, 미리 작성된 공급 경로와
  한 사건으로 서비스 권역, 전기 사고, 공간 공통원인, 내부전원과 정산을 검증했다.
- [수동 선로 건설](scopes/SCOPE_1_INTERACTION.md)은 고정된 출발점·도착점 사이에 지지물을 직접
  놓고 거리 제한을 지키며 발주·완공하는 상호작용을 검증했다.

둘은 의도적으로 별도 Core 세션, 데이터와 Godot 장면이다. 정확히 두 수요처, 고정된 회랑이나
고정 endpoint 같은 가정을 범용 제품 모델로 확장하지 않는다. 과거 구현과 자동검사는 회귀
기준으로 보존하고, 첫 단계에서 작은 제품용 권위 경로를 새로 시작한다.

## 2. 완성으로 부를 최소 2D 제품

1.0은 한 지도에서 이어지는 세 장의 짧은 캠페인이다.

1. **첫 점등**: 변전소와 선로를 직접 지어 마을에 처음 전기를 공급한다.
2. **두 번째 심장**: 병원에 주 경로와 실제로 독립적인 예비 경로를 만들고 비용을 감당한다.
3. **열돔 아래**: 공장 수요 증가, 예방정비와 예고된 폭염·노후 회선 사용불가에 대비한다.

플레이어는 한 종류의 가스발전소, 배전 변전소, 지지물과 선로를 직접 배치한다. 공사는 비용과
시간을 사용하고 완공 전에는 전기를 전달하지 않는다. 마을·병원·공장은 미리 배치된 수요처이며,
단순 연결과 경로 병목으로 공급을 판정한다. 잘못 만든 초안은 발주 전에 수정·취소할 수 있고,
완공 뒤 되돌릴 수 없는 설계는 처음부터 제공하는 `현재 임무 다시 시작`으로 복구한다. 캠페인
골격이 생기면 이 동작이 장 재시작이 된다.

병원에는 이중 경로와 제한된 UPS·디젤이 있다. 마지막 장에는 고정된 폭염, 이름 붙은 노후 회선의
사용불가와 예방정비 한 종류가 있다. 판매, 발전비, 미공급 보상과 현금 결산을 제공하며, 예고
타임라인과 `왜?` 설명이 선택과 결과를 연결한다.

제품 골격에는 새 게임·이어하기, 안전 경계 저장, 장 재시작, 화면·UI 크기와 조작 도움말 설정이
포함된다. 최종 단계에서 원본 2D 아트, 최소 VFX·SFX, 음량 설정, 라이선스 고지와 설치 가능한
빌드를 만든다.

### 1.0에서 제외하는 것

- 완공 자산의 철거·부분 선로 편집·재사용·salvage
- 위기 중 유상 공장 수요감축
- 3D, 별도 아이소메트릭 카메라 시스템, 절차 생성과 sandbox
- 여러 발전 기술의 포트폴리오, 배터리와 수동 발전기 출력
- DC/AC 전력조류, 연속 열·주파수·전압 simulation과 외부 solver 런타임 의존
- 확률 고장, 숨은 주사위와 상세 수리 logistics
- 여러 공사팀과 drag scheduler
- cloud 저장, 계정, 업적, replay 제품, multiplayer와 live service
- 프로젝트 금융, 원전·데이터센터·공유 냉각수
- 대화 tree, cinematic, voice-over와 범용 localization framework

철거는 초안 수정과 현재 임무·장 재시작만으로 실제 플레이가 막힌다는 관찰이 생길 때, 유상 수요감축은
예고·정비만으로 위기 선택이 성립하지 않는다는 관찰이 생길 때만 로드맵을 고쳐 다시 검토한다.
제외 항목은 자동으로 다음 버전의 backlog가 되지 않는다.

## 3. 구조와 규칙 원칙

### 하나의 권위 제품 경로

첫 통합 단계부터 다음 네 진입점을 하나씩만 둔다.

- 현재 활성 시나리오의 권위 데이터 root 한 개. 캠페인 단계에서만 장별 데이터를 참조하는
  campaign root로 감싼다.
- 엔진을 참조하지 않는 제품 상태 aggregate 한 개
- 기본 실행 Godot 진입 장면 한 개
- 현재 제품과 동결 회귀를 함께 실행하는 표준 검증 명령 한 개

이는 거대한 JSON, C# 파일, Godot script나 검사 파일 하나를 뜻하지 않는다. 그래프·건설·경제
규칙 모듈, Godot child scene과 검사 suite는 책임에 따라 나눌 수 있다. 금지하는 것은 같은 제품
규칙을 따로 계산하는 병렬 엔진과 별도 제품 흐름이다.

기존 Scope 0B와 Scope 1 타입은 회귀용으로 남기며 제품 타입의 기반 클래스나 공용 command bus로
만들지 않는다. DI container, ECS, plugin 시스템, 범용 편집기, 미래 저장 field와 사용하지 않는
interface도 미리 만들지 않는다. 범용 추상화는 실제 반복이 생긴 뒤 검토하되, 불변식과 생명주기가
다른 책임을 파일·타입으로 나누는 것은 반복 횟수와 무관하다.

### 단계별로 처음 필요한 의미만 동결한다

모든 미래 규칙을 먼저 설계하는 별도 0단계는 만들지 않는다. 대신 각 규칙은 처음 사용하는 단계의
계약과 단일 데이터 권위에서 구현 전에 고정한다. 다음 최소 원칙은 제품 경로 전체에 유지한다.

- 시운전되고 사용 가능한 설비만 방향성 terminal graph의 공급 경로에 참여한다.
- 수요처는 작성된 우선순위와 안정된 식별자 순서로 처리한다.
- 한 수요처는 결정론적으로 고른 한 경로로 전량 공급되거나 미공급된다. 부분공급과 여러 경로로의
  분할은 없다.
- 선택된 경로는 발전원과 선로의 남은 용량을 예약하며 동률은 안정된 식별자로 푼다.
- 여러 발전원이 처음 생기는 단계에서 고정 merit order와 정격 상한을 함께 동결한다.
- 선이 공간에서 교차해도 terminal이 없으면 접속되지 않는다. 지지물과 span은 여러
  `LineProject`가 공유하지 않는다.
- 공간 사건을 처음 여는 단계에서는 authored 위험 polygon과 span의 교차를 한 규칙으로 정하고,
  span 하나라도 닿은 전체 `LineProject`를 사건 동안 사용불가로 만든다.
- 공급 여부, 현금과 화면의 첫 실패 이유는 같은 Core 판정 결과를 사용한다.

서비스 권역의 기하 판정은 첫 점등 단계, 공유 용량·복수 경로와 공간위험 판정은 병원 단계,
복수 발전원 자동급전은 발전소 단계에서만 정확한 데이터와 경계값을 동결한다.

### 규칙과 화면의 경계

Core는 배치 가능 여부, 연결, 용량, 시간, 현금과 원인을 계산한다. Game은 pointer를 정수 grid
위치로 한 번 변환하고 Core preview·command를 호출한 뒤 반환 상태를 그린다. Game이 거리, 전력,
비용이나 사건 결과를 다시 계산하지 않는다. runtime 데이터에는 검사용 정답이나 witness를 넣지
않고 검사 코드가 소유한다.

## 4. 단계 요약

```text
첫 점등 통합
→ 병원 신뢰도·경제
→ 공장 수요와 발전소 용량 확장
→ 예고된 폭염·정비
→ 캠페인 골격·저장·기본 설정
→ 세 장 콘텐츠 고정
→ 2D 표현·사운드·패키징
```

의존성은 이 한 줄뿐이다. 중간 단계를 병렬로 구현하거나 뒤 단계의 schema와 UI를 미리 만들지
않는다.

## 5. 단계 1 — 첫 점등 통합본

### 플레이어 결과

하나의 native 지도에서 기존 발전원으로부터 시작한다.

```text
변전소 초안 배치·수정·취소
→ 견적 확인·발주·완공
→ 완공된 terminal 사이의 선로 초안 작성·되돌리기·취소
→ 견적 확인·발주·완공
→ 마을 점등과 첫 결산
```

변전소와 선로를 한 package로 묶거나 계획 terminal에 미리 선로를 발주하지 않는다.

### 포함

- 기존 온라인 발전원과 고정 접속 terminal
- 플레이어가 배치하는 배전 변전소 한 종류
- 직접 배치하는 지지물·선로 한 종류와 한 개의 마을
- 정수 grid, 부지·충돌·인접 구간 최대 길이, 고정 서비스 권역 규칙
- 한 개의 공사 자원, 비용·공기·현금과 원자 시운전
- 발주 전 비용·완공시각·연결 결과 preview
- 현금 부족을 포함한 거부 원인과 거부 시 상태·시간·현금 불변
- 완공 뒤 잘못된 설계를 복구하는 현재 임무 다시 시작
- 실제 인도 전력만 매출로 계산하는 짧은 결산
- 지도, 선택 상세, 공사 상태와 결과를 한 흐름으로 보여주는 UI

### 제외

발전소 신규 건설, 병원, 사건, 공장, 완공 자산 철거, 저장과 캠페인은 열지 않는다.

### 검증과 완료

- 서비스 권역 기하, 단일 수요 공급경로와 오류 우선순위를 단계 계약에서 먼저 고정한다.
- 부지·충돌·거리·endpoint, 초안 편집, 현금, 실패 불변, 임무 재시작, 공사 중 무전압, 완공
  원자성과 결산을 자동검사한다.
- 실제 map input과 표준 버튼을 지나는 native 흐름을 확인한다.
- 처음부터 container·anchor 기반 가변 창을 사용하고 1280×720과 1920×1080에서 clipping·text
  overflow, keyboard focus, 핵심 접근성 이름과 색 이외 상태 표현을 확인한다.
- 현재 제품 전체 검사와 Scope 0B·Scope 1 동결 회귀가 함께 통과한다.
- 향후 외부 테스트에서는 처음 보는 사람이 `배치 → 별도 발주·완공 → 연결 → 점등`과
  `권역 ≠ 공급`을 어떻게 이해했는지 관찰한다. 현재 개발 목표에서는 `NOT_COLLECTED`로 남긴다.

새 게임에서 첫 결산까지 한 기본 흐름으로 끝나고, 다음 단계가 의존하는 조작에 열린 core-flow major
문제가 없어야 한다.

## 6. 단계 2 — 두 번째 심장: 병원 신뢰도와 경제

### 플레이어 결과

병원에 주 경로와 예비 경로를 직접 만든다. 전기 설비 하나의 사용불가와 같은 공간 회랑을 잃는
사건이 다르다는 것을 지도에서 판단하고, 병원 내부전원·전력회사 공급·서비스·현금을 각각 본다.

### 포함

- 마을과 병원, 병원 UPS·디젤
- 직접 만든 복수 `LineProject`, 공유 용량과 결정론적 경로 선택
- 선로 project별 전기 회로 경계와 authored 공간 위험 polygon
- 판매, 발전 변동비, 미공급 보상과 현금에 반영하지 않는 LostSales 진단
- 선택·사건·결산의 `왜?` 설명

필수 안전·공급 의무는 hard condition으로 둔다. 기말 현금은 의무를 통과한 설계의 결과로 나란히
보여주며, 가중 총점이나 별점으로 병원 안전과 돈을 교환하지 않는다.

### 제외

부분부하 차단, 수동 switch, 확률 고장, 상세 보호계전과 전력조류 solver는 열지 않는다.

### 검증과 완료

공유 병목의 용량 예약, 경로 tie-break, 전기 단일고장과 공간 제거, 내부전원 비판매, 에너지·현금
보존과 첫 실패 원인을 자동검사한다. 작은 authored 전략 표로 불가능한 설계와 명백한 지배전략도
검산한다.

처음 보는 외부 사람이 직접 만든 두 경로의 공간 독립성, 비용 차이와 병원 결과를 설명하지 못하면
다음 기능을 열지 않고 이 단계의 정보 구조를 단순화한다. 이는 별도 점수 gate가 아니라 이 단계의
완료조건이다.

## 7. 단계 3 — 공장 수요와 발전소 용량 확장

### 플레이어 결과

짧은 장 시작 briefing에 적힌 공장 증설이 이미 발효돼 기존 공급이 부족하다. 플레이어는 한
종류의 가스발전소를 두 허용 부지 중 하나에 놓고 발주·완공·접속한다. 가까운 부지는 고정
부지비가 높고 선로가 짧으며, 먼 부지는 부지비가 낮지만 선로가 길고 완공이 늦다. 읽기 전용
예고 타임라인은 다음 단계 전까지 만들지 않는다.

### 포함

- authored 공장과 고정된 용량 부족
- 가스발전소 한 종류의 footprint, terminal, 정격, 건설비·공기와 변동비
- 상충관계가 있는 두 개의 허용 부지와 결과 preview
- 기존 발전원과 신규 발전원의 고정 merit order 자동급전

### 제외

자유 토지가격, 여러 발전 기술, 수동 출력, 기동 제약, 연료 조달, 주민정치와 상세 발전소 운영은
열지 않는다.

### 검증과 완료

부지 밖·겹침을 거부하고, 미완공·미접속 발전소는 출력하지 않으며, 용량 경계, source dispatch,
원자 편입과 인도 전력만 매출이 되는 규칙을 자동검사한다. 두 허용 부지는 어느 하나가 비용·공기·
연결에서 모두 우월하지 않아야 하며, 선택한 위치가 실제 임무 결과를 바꿔야 한다. 그렇지 않으면
기능을 늘리지 않고 부지 조건을 다시 본다.

## 8. 단계 4 — 열돔 아래: 예고된 폭염과 정비

### 플레이어 결과

플레이어는 읽기 전용 타임라인을 보고 공사와 예방정비의 순서를 정한다. 폭염과 이름 붙은 노후
회선의 사용불가가 오기 전에 준비하고, 위기 평가 경계 뒤 이전 결정이 서비스와 돈을 어떻게
바꿨는지 본다.

### 포함

- 결정이 있는 이정표 사이의 시간 진행과 중요 경계 자동정지
- 한 개의 공사 자원과 겹칠 수 없는 공사·정비
- authored 냉방 수요 증가와 노후 회선의 고정 유효정격 감소
- 노후 회선의 `정상 → 사용불가 → 복구` 사건
- 완료하면 그 예정 사용불가를 막는 예방정비 한 종류
- readable forecast timeline과 사건 결과 보고

연속 1분 시계는 분 단위 선택이 실제로 필요하다는 관찰 전에는 만들지 않는다. 폭염의 수요 증가와
정격 감소는 각각 손검산·회귀한 뒤 통합한다.

### 제외

위기 중 수요감축, 확률 고장, 연속 열모델, 배터리, 블랙스타트, 상세 수리와 drag scheduler는 열지
않는다.

### 검증과 완료

같은 경계의 사건 순서, 기한 가능성, 공사 자원 배타성, 정비 효과, 사용불가·복구·정산과 모든
실패의 상태 불변을 자동검사한다. 외부 관찰에서는 사건이 숨은 주사위가 아니라 이전 선택의
결과로 읽히는지와 위기 전에 실제로 바꿀 선택이 있었는지 기록한다. 선택이 의미 없으면 수요감축
기능을 바로 추가하지 않고 현재 예고·정비 구조를 먼저 다시 본다.

## 9. 단계 5 — 캠페인 골격·저장·기본 설정

### 플레이어 결과

`Title → New Game/Continue → Pause → Save & Quit → Continue/Restart Chapter` 흐름과 화면·조작
설정을 사용할 수 있다.

### 포함 순서

```text
campaign root와 현재 chapter ID
→ 장 사이 carry-over와 장 시작 checkpoint
→ 저장 가능한 안전 경계
→ version을 가진 JSON과 atomic replace
→ Title·Continue·Save & Quit
```

저장은 이 단계에 실제로 존재하는 상태만 기록한다. 캠페인 root 하나가 장별 authored 파일을
참조할 수 있으며 모든 장을 거대한 JSON 한 파일에 넣지 않는다.

### 포함

- 캠페인 슬롯 한 개와 `Restart Chapter`
- 안전 경계 autosave와 `Save & Quit`
- 창/전체화면, UI scale과 조작 도움말 설정
- 한국어 단일 언어

이 단계를 열기 전에 실제 지원할 운영체제를 정한다. 그 전에는 현재 검증 환경만 밝히고 검증하지
않은 플랫폼을 지원한다고 광고하지 않는다.

앞 단계의 `현재 임무 다시 시작`은 이 단계에서 장 시작 checkpoint를 사용하는 `Restart Chapter`로
이어진다.

### 제외

음량 설정은 실제 사운드를 넣는 마지막 단계까지 미룬다. cloud, replay, 계정, 여러 profile,
achievement와 범용 migration framework도 열지 않는다.

### 검증과 완료

모든 현재 공사·사건 경계의 저장 round-trip, 저장 직전·재개 직후 결과 동일성, 잘린 파일·손상
파일·알 수 없는 version의 안전한 거부와 설정 지속을 자동검사한다. 강제종료 뒤 마지막 안전
경계로 돌아오고 손상된 저장이 새 게임 시작까지 막지 않아야 한다.

## 10. 단계 6 — 세 장 캠페인 콘텐츠 고정

### 플레이어 결과

같은 지도와 이어지는 망 상태로 `첫 점등 → 두 번째 심장 → 열돔 아래`를 처음부터 끝까지 플레이한다.
짧은 업무 브리핑, 예보, 마감과 결과 보고가 이야기의 전부다.

### 포함

- 각 장의 시작 상태, 의무, 기한, 사건과 최소 한 개 reference completion
- 이전 장 자산·현금의 명시적 carry-over와 최소 준비금 검산
- 상황에 맞는 짧은 tutorial과 언제든 다시 보는 도움말
- 의도된 실패, 장 재시작과 softlock 방지

hard condition을 평가하는 경계에서 의무를 만족하지 못하면 명시적으로 실패하고 `Restart Chapter`를
제공한다. `softlock`은 다음 의무에 도달할 방법이 없는데 실패나 재시작도 제시되지 않는 상태다.
일반 해법 탐색기를 만들지 않고 authored 시작·carry-over·위기 경계의 reference 상태만 검산한다.

### 제외

인물 대화 tree, cutscene과 voice-over는 열지 않는다. 같은 시스템을 새롭게 조합할 가치가 확인되지
않으면 고정 challenge도 출시조건에 넣지 않는다.

### 검증과 완료

reference completion, 의도된 실패·재시작, carry-over, 기한·최소 공기, 중복정산과 softlock 부재를
자동검사한다. 전체 캠페인 관찰에서는 이해, 공정성, pacing과 다시 하고 싶은 이유를 기록하되
통계적 합격률로 포장하지 않는다. 콘텐츠를 고정한 뒤에는 새 mechanic을 추가하지 않고 모든
briefing의 약속과 실제 규칙을 일치시킨다.

## 11. 단계 7 — 2D 출시 품질과 패키징

### 플레이어 결과

산업 생존 분위기의 원본 2D 지도·설비·상태 overlay와 최소 VFX·SFX가 적용된다. 지원한다고 명시한
운영체제의 깨끗한 설치에서 세 장 캠페인을 끝내고 저장·재개할 수 있다.

### 포함

- 단계 1부터 유지한 가변 layout·focus·접근성의 최종 typography와 clipping 검수
- 통전·계획·공사·사용불가를 색과 pattern·label로 함께 표현
- 1280×720과 1920×1080 16:9, UI scale과 한국어 typography
- 차단기·점등·사용불가와 최소 ambient SFX, master·ambient·SFX 음량 설정
- credits, 제3자 자산 목록, 라이선스와 설치 안내
- 실제 지원 플랫폼별 설치 가능한 package

카메라 이동, 3D, cinematic, voice-over와 localization framework는 실제 가독성·출시 요구가 없으면
추가하지 않는다.

### 검증과 완료

clean checkout build, 전체 회귀, package smoke, 화면 layout, 성능·메모리 예산을 검사한다. 지원하는
각 운영체제에서 fresh install, save/resume, display/audio/input과 전체 캠페인을 수동으로 확인한다.
열린 critical, major, softlock과 data-loss가 모두 0이어야 한다. 알려진 minor issue,
최종 build 식별값, changelog, 라이선스와 설치 지침을 남긴 뒤 소유자가 출시를 수용한다.

## 12. 검증과 종료 정책

### 네 종류의 증거

- **기계 검증**: schema, 거리·경로·용량·현금·에너지 보존, 상태전이, build와 저장 손상을 검사한다.
- **native 확인**: 개발자나 소유자가 실제 입력 경로로 현재 단계의 핵심 행동을 한 번 수행한다.
- **외부 관찰**: 구현에 참여하지 않은 사람이 무엇을 이해하고 어디서 막히는지 기록한다.
- **독립 검토**: 새 문맥에서 코드·데이터·증거·문서의 범위와 충돌을 검토한다.

외부 관찰은 첫 점등, 병원 신뢰도, 전체 위기 흐름, 세 장 콘텐츠 고정과 release candidate처럼
자동검사가 답하지 못하는 지점에만 둔다. 참가자 수나 통과율 목표는 미리 만들지 않고, 관찰된
혼란과 심각도를 기록한다.

현재 사용자가 승인한 개발 목표는 외부 테스트를 시작하기 직전까지다. 따라서 각 구현 단계는
기계 검증·native 확인·독립 검토를 마치고 외부 관찰을 `NOT_COLLECTED`로 명시한 채 다음 단계로
넘어갈 수 있다. 이는 관찰을 통과한 것이 아니며, 전체 제품 테스트와 출시 판단은 외부 관찰 전에는
열리지 않는다.

`critical`은 crash, data loss, softlock 또는 핵심 흐름 완료 불가다. `core-flow major`는 다음
단계가 의존하는 판단·조작을 막거나 잘못 이끄는 문제다. 그 밖의 `major`는 핵심 흐름을 끝낼 수는
있지만 의미 있게 잘못된 결과나 큰 불편을 만드는 문제이고, `minor`는 명확한 우회가 있는 불편이다.

### 공통 종료조건

모든 단계는 다음을 충족해야 한다.

1. 해당 단계의 기계 불변식과 현재 제품 전체 회귀가 통과한다.
2. Scope 0B와 Scope 1 동결 회귀가 통과한다.
3. 핵심 native 흐름을 실제 입력으로 확인했다.
4. 미해결 critical과 다음 단계가 의존하는 core-flow major가 없다.
5. 비핵심 major를 남긴 경우 수용 이유와 다시 볼 조건을 기록했다.
6. 로드맵이 지정한 외부 관찰을 마쳤거나, 현재의 테스트 전 개발 목표에서는 `NOT_COLLECTED`로
   남겼다.
7. README·영향받은 문서를 현재 상태에 맞추고 독립 검토를 마쳤다.

LLM 플레이는 단계별 기본 완료조건이 아니다. 자동검사와 native 확인 뒤에도 한 문장짜리 상호작용
질문이 남을 때만 최대 한 번의 임시 smoke를 별도 승인한다. 불리한 결과를 교체하거나 재실행하지
않고 사람·밸런스·출시 증거로 사용하지 않는다. transcript·runner·manifest 체계를 새로 만들지
않는다.

## 13. 로드맵 중단 조건

단순 연결과 capacity 규칙이 관찰된 결과를 설명하지 못하거나, 서로 구별되는 전략이 세 개 이상
생겨 손검산이 실제 개발을 막을 때만 로드맵을 멈추고 물리 또는 정적 밸런스 도구를 별도 검토한다.
그 전에는 상세 전력조류, Thermal Lab, Battery Lab과 자동 튜닝을 열지 않는다.

단계 중간에 더 큰 기능이 필요해 보여도 현재 완료조건을 조용히 바꾸지 않는다. 기능을 빼고도
플레이어 결과가 성립하는지 먼저 확인하고, 필요성이 관찰로 남았을 때만 로드맵을 수정해 별도
승인을 받는다.
