# Gridworks repository rules

## Read first

Before changing implementation or balance data, read in this order:

1. `SCOPE_0_PLAYABLE.md`
2. the relevant rules in `GAME_DESIGN_KO.md`
3. `SCOPE_1_0.md` only to understand unopened candidate gates
4. `BALANCING_STATIC_SIM.md` before proposing automated tuning
5. `POST_1_0.md` before proposing scope expansion

## Scope

- The current authorized milestone is **Scope 0 Player Test only**. Implement only
  `SCOPE_0_PLAYABLE.md` unless the user explicitly approves a later adaptive checkpoint.
- A completed Scope 0 authorizes a review, not automatic work on the next candidate gate.
- Do not pre-build post-1.0 systems as speculative infrastructure.
- Treat concept PNGs as visual references, never as numeric or rules authority.
- Do not implement free-route drawing, DC power flow, thermal protection, batteries, peakers, preventive
  maintenance, repairs, a 120-day campaign, save/replay, a Static Balance Lab, production 3D, or extra
  project assemblies in Scope 0.
- Nuclear projects, data centers, cooling-water distance, and water/air cooling are post-1.0 only. Do not
  add their contracts, schemas, commands, UI, or placeholder fields before that milestone is explicitly opened.
- If that milestone opens, preserve one `CoolingWaterZone`, one linear distance-overhead rule, one hard cutoff,
  and two data-center cooling states. Water networks and data-center internal management remain out of scope
  unless a later adaptive planning checkpoint explicitly changes the boundary.

## Architecture

- Keep the authoritative simulation in pure C#/.NET with no Godot reference.
- Scope 0 starts with `Gridworks.Core`, a minimal Godot 2D prototype under `game/`, one scenario file, and
  tests. Do not create `Application`, `Persistence`, or `Headless` projects until their gate is opened.
- Godot sends commands to Core and renders returned state; it never mutates authoritative state directly.
- Scope 0 uses a simple capacitated graph and integer game minutes. Do not add a general solver as future-proofing.

## Data and determinism

- Before the first code commit, the fixture table and oracle in `SCOPE_0_PLAYABLE.md` are Scope 0's numeric
  authority. From the first code commit onward, the single `data/scenario.json` becomes the sole machine
  authority. Do not duplicate its values in C# or Godot scenes, but do not build a general schema registry yet.
- Use stable IDs, deterministic ID-sorted iteration, integer game minutes, integer money, and exact energy units.
- There is no authoritative random stream. Demand, warnings, and outages are authored data. Maintenance
  windows become authored data only if a later timeline gate opens them.
- Save/replay hashes and cross-platform byte identity are not Scope 0 requirements.
- When numerical power flow is later opened, same-build/runtime/architecture output must be byte-identical;
  cross-platform contracts apply to quantized game outcomes, not raw floating-point bytes.

## Balance changes

- Do not ask an LLM to tune autonomously toward a scalar score.
- Scope 0 has zero active `BalanceKnob` values and no automated sweep. Treat every fixture number as an
  unverified assumption and change only one rule or parameter family per human-test round.
- A small hand/static sanity table may verify units, budget, capacity, obligation activation versus earliest
  completion, warning lead time, and obvious plan dominance. It must not grow into an optimizer before the
  player-choice gate passes.
- When a Static Balance Lab is explicitly opened, classify parameters and sweep at most three active knobs at
  once. The absolute maximum for every later milestone is six, with no exception.
- Use human playtests to approve comprehension and fun. Automated tools may reject impossible candidates but
  never stand in for player behavior.
- Commit each balance decision with hypothesis, parameter family, tested bounds, result, available human
  evidence, and remaining risk.

## Verification

- Add or update only the deterministic unit, scenario, and Godot smoke tests required by the active gate.
- Run formatting, build, all relevant tests, and the active gate's smoke test before claiming completion.
- Do not require unopened save/replay, Headless, schema, capture, or production-performance suites.
- Do not enter the next implementation gate until the current gate's criteria are met.

## Adaptive planning checkpoint

There is no complete plan that should be executed unchanged from beginning to end. After completing every
major development unit or implementation gate, pause before starting the next one and:

1. summarize the implementation, automated checks, performance measurements, playtest evidence, surprises,
   and remaining risks from the unit just completed;
2. check which assumptions in the current plan were confirmed or disproved;
3. review the next development unit's scope, ordering, dependencies, parameter budget, tests, and definition
   of done;
4. update the active plan and the relevant scope/design/decision documents when evidence calls for a change;
5. explicitly record work that was deferred, removed, or newly justified.

Keep only the next major unit detailed; later units stay coarse. Passing a gate authorizes this review, not
automatic execution of the old next step. Do not expand scope merely because a future system was mentioned
in `POST_1_0.md`.
